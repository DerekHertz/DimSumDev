# Protected task-tree execution

The hierarchy is Bao (Claude) or Jiao (Codex), up to four role managers, and up to four runners per manager. It bounds the decomposition; it does not prescribe how many processes to start. A small task normally uses its owner alone or one helper, while required independent reviews still run. Configured owner/manager models keep planning and judgment; lower-cost runners do bounded work whose evidence their manager checks.

## Current architecture and this slice

`.claude/agents/*.md` owns role contracts and Claude model/effort settings. `scripts/codex-sync.mjs` generates `.codex/agents/*.toml`, adapting runtime prose while preserving tiers. Its existing mapping is Sonnet → `gpt-6.1-sol`, Haiku → `gpt-6-luna`, Opus → `gpt-6-astra`. The orchestrator and judgment roles use Sonnet/high; runner and scout use Haiku/low; SRE uses Haiku/medium. This change chooses no new owner tier. `.claude/skills/` generates `.agents/skills/`; `CLAUDE.md` and `.codex/runtime-guidance.md` generate `AGENTS.md`.

The opt-in managed workflow adds fixed tree proposals, explicit revision approval, parent-scoped child requests, configured model routing, isolated worktrees and descendant cancellation. It shares existing admission, ownership, runtime allowlist, governance and resource checks. Native Claude Agent/Task delegation is disabled. Nodes default to read-only execution; an approved runner can use `executionMode: "code"` to edit existing canonical file or directory scopes. A new file requires an existing scoped parent directory. The launcher mounts the remaining worktree read-only and rejects protected paths, symlinks, hard links and unsupported scope shapes. Runners receive no commit, publication, grant or child-delegation rights.

Completion evidence is bound to exact approved criteria and literal verification commands. The bridge captures immutable candidates only after confirmed resource-group cleanup. Fresh review phases use their trusted higher-tier roles and the existing code, QA, risk, security and human-verdict floors. An author cannot review itself, choose a cheaper reviewer, change the candidate or submit an acceptance boolean. Failed checks or bounced reviews pause work; this workflow creates no automatic author retry or correction allowance. Actual code leaves and final integration require other-runtime verification by default. An unavailable verifier pauses acceptance until the user makes an attributable exact-candidate same-runtime choice; that choice preserves the fresh session, configured model and review floor.

The existing process policy remains `worker: 2`, `bao: 1`, `scout: 1`, shared across runtime identities. These are process classes, not tree layers. Approved child requests queue when capacity is busy. An owner or manager can yield to a direct-child barrier, releasing its execution session while children run and receive independent verification. The bridge integrates accepted child candidates in stable order while their parent's worktree is stopped, then wakes the same logical parent in a new attempt. Approved sibling dependencies wait for their accepted prerequisite to be integrated into the execution base. Waiting and review-queued logical nodes still count toward the separate global budget of 21 unfinished admitted nodes. This does not enable ADR0029's proposed 2-executive/4-manager/8-runner simultaneous profile.

There is no production Codex adapter on the starting main branch. Codex identity tests through an injected adapter prove the host contract only. Live Codex execution remains unavailable until codex-residents/16 builds the disabled protected app-server adapter/shared policy compiler, den-mvp/72 proves the actual launch path, and codex-residents/02 independently reviews enablement. Registration is a separate gated change. Mixed-runtime review admission is also a remaining integration stage under codex-residents/06; adding a second adapter alone does not turn the current verification pause into automatic cross-runtime execution. The native per-turn workspace sandbox alone lacks credential-deny/read-root controls and is not a substitute for a verified named-permission-profile compiler. The production resource launcher also requires Linux cgroups v2 and bubblewrap; native Windows cannot provide its live conformance evidence.

## API and approval

The existing ticket approval first records the task's owner. Session-authenticated `POST /trees/plan` proposes `{ ref, runtime, project, scopes, nodes, rootContract? }` without starting a process. The optional root contract contains `{ outcome, inputs, acceptanceCriteria, verificationCommands }`; otherwise criteria must come from approved ticket checkboxes. Missing acceptance criteria cannot be accepted. Root runtime must match its recorded owner. Each non-root node has `{ id, parent, role, outcome, inputs, scopes, dependencies, acceptanceCriteria, verificationCommands, executionMode? }`. `parent` names `owner` or a manager contract ID. `dependencies` names approved siblings. Runtime and model/effort come from trusted control recipes, frozen in the proposal. Scopes stay within their parent's approved scope; unknown parents, cycles, excess depth/fanout and governed escapes are refused.

Review the returned complete revision. Session-authenticated `POST /trees` with `{ revision }` explicitly approves that exact revision and starts its owner. A later proposal supersedes an unapproved revision. Agent credentials cannot approve revisions or choose a new owner. A changed ownership epoch, disabled runtime or unavailable configured model refuses execution; there is no automatic runtime/model fallback.

Tree runs receive a private MCP capability. Its token fixes the live node and phase; requests cannot supply another parent, role, runtime, model, scope or grant. `delegate({ nodeId })` requests an approved direct child. `result({ childId })` reads its status/evidence; `status({})` reads the fixed plan. `yield({ children })` establishes a direct-child barrier. `complete({ criteria, checks, unused? })` submits author evidence; `review({ candidate, verdict, criteria, checks, findings, guardVerdicts? })` belongs only to a fresh trusted review phase. Review phases retain reporting/status tools and cannot delegate. `skip({ nodes })` lets the owner omit complete never-started subtrees or a manager omit its own never-started direct runners. Required criteria, reviews, requested work and dependencies of retained nodes cannot be skipped. Managers can therefore use fewer than their approved maximum runners while their owner is waiting.

Each attempt uses a private worktree. Managed checkout and clean checks operate on raw Git blobs without repository-selected filters, hooks, fsmonitor, EOL or encoding transformations. Candidate receipts and hook state are protected from every new managed or legacy native launch; existing unprotected or unsettled processes block managed-tree admission. Live sibling write scopes must be disjoint. Explicit cancellation and shutdown cancel descendants, including a late spawn. Yield is a recorded suspension, not cancellation. Unconfirmed resource cleanup blocks capture, integration and further admission.

Session-only `POST /trees/verifier` takes `{ revision, nodeId, candidate, runtime, reason }` to record an exact-candidate same-runtime verification override. It does not waive independent review. `POST /trees/verdict` takes `{ revision, nodeId, candidate, verdict }` for the existing required human gate. Agent, service and den credentials cannot exercise these choices. `POST /trees/resume` takes `{ revision }`; it validates the full contract, current owner epoch/models/scopes, protected receipts and stopped resources. Historical approvals/reviews alone never restore authority; acceptance is reverified in fresh review attempts. Unknown author outcomes remain paused. Ended tree sessions cannot use legacy conversation resume.

`GET /trees` is session-authenticated. It contains the reviewed contracts and current node states; treat it as private task data. It is not a public replay feed. A process completion does not satisfy a required independent code/QA/security review, acceptance criterion, integration barrier or publication gate. Existing first-failure, one-attempt, correction-budget, scoped-test and user-merge rules still apply.

Ordinary startup must continue reporting Codex unavailable until its enablement gates pass.
3. Measure mixed workloads within the current aggregate resource budget before proposing any higher live-capacity profile. The 21-node structural limit remains independent of those measurements.

The current implementation authorization covers reversible code work on these stages. Linux launch-path conformance is still required; available WSL tools or a resource preflight alone do not prove a live runtime. The existing separate enablement/user-merge gate remains. Dependency additions, account/credential changes, publication, owner-tier changes and unmeasured resource-limit increases retain their existing approval requirements; this slice adds none of those approvals. The complete-revision approval above is the existing codex-residents spec's explicit requirement (user story 10 and "no unapproved decomposition execution"), not a requirement to spawn every approved node.

### Separate Codex adapter change

The smallest Codex implementation is a disabled adapter in a separately reviewed change. First extract the runtime-independent permission compiler while retaining Claude's behavior. Then implement a bounded app-server protocol with correlated requests, exact thread acknowledgements, explicit unknown-request denial and bounded approval decisions. Use the existing resource launcher with private native state, protected credentials and trusted recipes; suppress inherited configuration and native delegation. Validate the configured model and effort against paginated native model capability responses. Resume requires exact thread identity, current ownership/authority and reconciled resource state. Cancellation, crash and shutdown must revoke capabilities and settle the entire resource group.

Fixture protocol tests precede actual filesystem, credentialed-connection, network, permission, resource and recovery tests through that launch path. The native per-turn workspace-write profile alone cannot encode the required credential-deny and readable-root restrictions. Session-wide approvals, permission/policy amendments and file `grantRoot` choices cannot be translated into an ordinary bridge Allow. Inspect and pin the actual installed native schema before implementing those decisions.

Reversible adapter implementation is covered by the user's request. Production registration is separate: [codex-residents/02](https://github.com/DerekHertz/DimSumDen-board/blob/main/codex-residents/issues/02-protected-codex-runtime.md) says, "Do not register Codex until01,72,16 and all actual launch-path protections pass." The separate reviewed user-merge gate and this task's report-before-publication restriction remain in force. No new dependency, credential, account or resource-limit change is implied by this plan.

## Lifecycle data for replay consumers

The bridge already appends `.scratch/_run/sessions.jsonl` and publishes agent state changes through `/events`. Tree records additionally live in `.scratch/_run/task-trees.jsonl`; proposals contain full contracts and must stay private. Neither JSONL file is a tamper-proof audit log. Replay validates records and never restores authority to signal a process or reuse a capability.

A visual consumer should project lifecycle records into a whitelist, rather than expose the journal, transcript, contracts or reports:

| Replay field | Source/meaning |
|---|---|
| `runId`, `agentId` | Bridge agent/run ID; do not use native session IDs as authority |
| `eventId`, `sequence` | Consumer source plus JSONL line ordinal, or its SSE sequence; identify the source because there is no global cross-store sequence |
| `timestamp` | Record `ts`; chronology is an observation, not proof of causation |
| `treeId`, `nodeId`, `parentId`, `layer` | Bridge tree metadata; layer maps depth 0/1/2 to owner/manager/runner |
| `role`, `runtime`, `model` | Trusted configured selection where recorded; lifecycle `role` and `configuredModel` describe the actual phase, while `logicalRole` identifies its structural task. Keep these distinct from model-reported usage. |
| `attemptId`, `phase` | One process attempt and its implementation, continuation or independent review phase; neither changes the logical node's structural parent or tier. |
| `kind`, `state` | Tree journal `proposed`, `approved`, `reserved`, `ended`, `workflow` checkpoints and explicit `lifecycle` records, or session `spawn`/`end`. Only an acknowledged `started` lifecycle record proves the recorded start; no synthetic review approval. |
| `taskSummary` | Omit by default; a separately redacted, bounded user-approved label only |
| `evidenceRefs` | Candidate SHA or explicit reviewed evidence reference when present; no raw reports, paths or prompts |

Do not emit tokens, credentials, raw task inputs, transcripts, shell commands, private native session stores or connection configuration. Missing model/review/evidence fields remain missing. Candidate-bound review reports and acceptance transitions are distinct events; a raw completion is never a review verdict. A separate visual integration must verify its projection against actual lifecycle output before presenting it as a recorded run.

### Mapping to the separate replay prototype

The separately developed `prototypes/hierarchy-audit` version-1 contract wraps events as `{ schemaVersion: 1, runId, label, illustrative, events }`. Its complete event shape is `{ runId, eventId, sequence, timestamp, agentId, parentId, name, role, layer, runtime, model, tier, kind, taskSummary, relatedAgentId, reason, blockedOn, commit, pr, evidenceRefs }`. It accepts at most 2,000 events and 1 MiB; sequence starts at one and timestamps must be nondecreasing UTC. `illustrative: false` means imported and unverified. It supplies no authentication or tamper evidence.

Integration needs an explicit export adapter, rather than a second runtime journal. Use the tree revision for `runId`, stable logical node IDs for the structural graph, and the existing journal position for stable source event IDs. Assign consecutive projection sequence numbers and identify that sequence as an export prefix, not a global audit sequence. Export only acknowledged starts and recorded state transitions; a reserved spawn is insufficient. Default summaries to generic layer labels unless a user has reviewed a bounded redacted label. Omit raw criteria, inputs, commands, reports, native session IDs and paths. Evidence references require a separately approved safe artifact mapping.

Version 1 cannot faithfully express every runtime record. A logical task can have several attempts and higher-model independent review phases, while the viewer makes runtime/model immutable per agent ID and permits only 21 identities. Do not overwrite a runner's model with its reviewer's model, invent a reviewer child beyond the structural depth, or call an active process `working` without that state being recorded. The viewer represents child acceptance as a parent event after a child result; host verification acceptance therefore needs an explicitly documented projection, without claiming that the parent authored an independent verdict. SHA-256 candidate IDs also exceed its 40-character commit field. Missing transitions, clock regressions, retries, omitted review phases and unsupported identifiers need explicit export diagnostics or a later contract version. No live UI, export endpoint, PR attachment or prototype integration is enabled by this runtime change.
