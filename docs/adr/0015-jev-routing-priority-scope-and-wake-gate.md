# Jev also labels route, priority, scope and the wake-up gate, each in shadow first; find is not built until the jg trial says so

> Terms: written before ADR 0028, which renamed the vocabulary (cell → agent, cell type → role, genome → role definition, station → team, organism → the org, apoptosis → hand off and exit).

**Status:** accepted for shadow (2026-09-30, architect, from `.scratch/organism-infra/spec.md`, settled with the user in a grilling session). **Numbered 0015, not 0012:** the user asked for "0012", but 0012 is `organ-renamed-station-brain-gate-renamed-pass-gate`, and 0013 and 0014 are taken. **Not yet decided:** the route and wake-up go-live bars (decisions 5 and 6 are proposals for the user's approval); every go-live also needs its own exit review and the user's yes. `security` reviews the Data exposure section before route (bounce half) and the wake-up gate make their first call, shadow included. **Amended** 2026-09-30: route runs advisory-live (Amendment 1, at the end). **Amended** 2026-10-07: trials replace shadow-first and the go-live bars; priority and scope are displayed suggestions; wake goes live (Amendment 2, at the end). **Amended** 2026-10-12 (proposed, not yet accepted): the frontier order becomes the Queue, a computed order with an active feature and an admission gate; decision 4's order and aging bump are replaced (Amendment 3, at the end).

**Context.** ADR 0010 gave Jev two decision points, `tier` and `verify`, both in shadow, and listed other decisions as "not Jev's". Shadow data so far is mixed: tier (24 tickets, 3 fallbacks) projects +11.7% tokens, so it costs more; verify (20 tickets, 0 fallbacks) projects -5.5%, median about 450 ms, so it saves. The orchestrator still spends Opus judgment and the user still spends attention on decisions that are cheap to label: who takes a new ticket, who a bounce goes to, which frontier ticket goes first, and whether a new input should wake the orchestrator. The mixed result means each point must earn live status on its own data, so points are added one at a time.

**Conflicts checked.**
- *ADR 0010 decision 1*, the "not Jev's" list. This ADR supersedes **only** that list, and only for: dispatch routing and board triage (now `route`), frontier order (`priority`, `scope`, new), and the wake-up check (`wake`). Still not Jev's: security review depth (`risk-check` decides), tool routing, scout filtering, parallel threads. 0010's `tier` and `verify` decisions, minimum tiers, cap, fallback, and exit criteria stand unchanged. Nothing here is an amendment to them.
- *ADR 0010 decision 9*, "never leaves the machine: ... handoffs". The spec has route send handoffs to Jev for bounces. That contradicts 0010's list, so decision 8 records it as an extension and holds the bounce half of route behind `security`. New-ticket route sends the ticket only, which is already an exposure class 0010 allows.
- *ADR 0014 (jevgrep).* Overlaps `find`; resolved in decision 9.
- *ADR 0001, 0004.* Hold: Jev is not the Claude API, and the script is plain Node.
- *Vocabulary.* The spec and `jev.mjs` both say "floor": `jev.mjs` already has a verify-depth `floor` (ticket 58: verify floors to full when qa never ran specify), and the spec adds budget "floors". This ADR calls the budget ones **reserved budget** to keep them apart from that and from **minimum tier**.

**Decision.**

1. **Authority rules (bind every point).** Jev picks only among options the state machine already allows. It may raise (to `security`, to full verify), never skip. It never bypasses a gate: user verdicts, the twice-failed stop, the 80% usage stop, the two-cell file-overlap rule. Where code can decide, code decides, and Jev judges only what code cannot. Routing goes live only over a closed label set with an `other` label, and `other` (like any failure, blocked input or cap) means the orchestrator decides. Every point ships in shadow mode and goes live only after its own exit review and the user's yes. Neither the label sets nor the go-live bars below are applied by a point until that yes.

2. **Shape: more points in one script, not more scripts.** Each point is a `point` value of `jev.mjs` (`route`, `priority`, `scope`, `wake`), reusing 0010's cap, redaction, blocked-input, fallback, exit-code and row rules (deletion test: separate scripts would copy all of them). The wake-up prelude is code that imports `decide` for its one ambiguous case; it does not reimplement the cap or the log. The model output is always mapped to a closed label set, and anything outside it becomes `other`. Code owns everything deterministic: state-machine exclusions, ordering, aging, gate conditions, budget arithmetic.

3. **Route** (`route`, slice 2).
   - New-ticket labels: `product | architect | designer | qa-specify | developer-direct | user | other`. Bounce labels: `developer | qa | architect | user | other`.
   - Never fires where the state machine dictates the next cell (for example in-review goes to qa verify). Code removes any label the state machine forbids for that ticket before the call; `developer-direct` exists only where today's relay already lets the orchestrator send a developer without qa specify (non-code tickets), and is never offered on a code ticket.
   - **Ground truth is read from the board, not self-reported.** Shadow stdout must not show the pick to the orchestrator (only the row carries it), or agreement measures anchoring, not judgment. The report joins the row to the next cell claim on that ticket (the board's claim events) and reads that cell as the actual dispatch. Slice 2 confirms the events carry the cell type; if they do not, it logs `actual` from the orchestrator and says so in the report.

4. **Priority and scope** (slice 3). Code keeps the frontier order: explicit `**Priority:** P0-P3` line (none means P2), then age, then number, with the aging bump after 3 orchestrator sessions. An explicit line always wins. Jev only flags mismatches (a ticket that looks P0 but is marked P3); filling a missing line is out of v1. Scope labels are `small | medium | large | other`; the combined order is computed in code (P-level, unblock count from Blocked-by edges, smaller scope, age) and scope never crosses a P-level. Shadow logs the order it would have used beside the actual order. Ground truth for scope is terciles of weighted tokens per ticket from `usage.jsonl`, recomputed each report, 0-baseline tickets excluded.
   - Flagging goes live at at least 70% user-verdict-right over at least 10 flags. Fills go live only after at least 20 fills with at least 80% "user would accept". Scope goes live at at least 60% same-tercile over at least 20 tickets, and no `small` pick was a `large` ticket in the last 10.

5. **Route go-live bar (proposal, for the user's approval; modeled on 0010 decision 10 and the priority and scope bars in decision 4).** Each half is judged separately, on tickets where a `route` row and an actual dispatch exist.
   - *Coverage:* at least 15 new-ticket rows; fallbacks (not counting `cap`) at most 1 in 5; median `ms` under 2000. Bounce half: at least 8 bounce rows (bounces are rarer), same fallback and latency limits; until then it stays in shadow while the new-ticket half may go live.
   - *Agreement:* at least 85% of non-`other` picks equal the actual dispatch, and `other` is at most 35% of rows (a point that mostly answers `other` saves nothing). The orchestrator reads each disagreement from the handoffs and marks it Jev-right, orchestrator-right, or either. A disagreement where the orchestrator's dispatch was itself the mistake (the ticket bounced for a wrong first cell) counts as agreement, and the report lists it.
   - *Safety:* no row where Jev's pick would have skipped a required cell (for example `developer-direct` on a ticket that ran qa specify, or a bounce label that would have skipped the verify or security stage the state machine requires). One miss keeps the point in shadow for 15 more tickets, or ends the trial.
   - *Spend:* the route reserved budget was never exhausted for a reason other than heavy use.
   - Live means the orchestrator dispatches to a non-`other` pick without spending its own judgment. Gates and the state machine still apply.

6. **Wake-up gate** (`wake`, slice 4). Code decides everything it can without calling Jev: frontier non-empty, usage under 80%, CI red or merge conflict, an open user-verdict gate request. Jev sees only inputs code has no rule for (a new file in `.scratch/_requests`, a ticket comment), with labels `needs-claude | informational | other`; `other`, blocked input and any failure wake the orchestrator. v1 is a session-start prelude script, not a daemon or timer.
   - *Tension to close in slice 4:* `informational` is the one label that suppresses a wake, which the raise-never-skip spirit of rule 1 disfavors, and a ticket comment can carry scope that counts as acceptance criteria. So code, not Jev, wakes on any comment authored by the user, any `Scope added` comment and any `--verdict` comment; Jev judges only the rest.
   - *Go-live bar (proposal, for the user's approval; the spec gives none):* at least 15 `informational` labels, and on none of them did the orchestrator later act on that input (the board shows a claim, comment or resolution traceable to it); plus the coverage and spend limits of decision 5. A single missed wake keeps the point in shadow.

7. **Budget.** One shared $0.50 daily cap (0010 decision 6). New: **reserved budget** of $0.05 per day each for `tier`, `verify` and `route`, inside the cap. A point spends its own reservation first, then may draw only from the unreserved remainder, which is $0.35 with three reservations; `priority`, `scope`, `wake` and later points share that remainder. No point can consume another's reservation, and the cap still overshoots by at most one call. Today `CAP = 0.5` is flat, so the reservations are new code; whether they ride with slice 2 or ship as a prep ticket is a ticketing choice. A point out of budget falls back to "orchestrator decides", logged `fallback:"cap"`.

8. **Data exposure (for `security`; extends 0010 decision 9).** Two channels with different providers, and both must state the same rule set.
   - *`jev.mjs` to TypeSafe's API via `TYPESAFE_API_KEY`:* 0010's ticket markdown and test output, plus, new here, handoff text for bounce routing (16k-character tail-truncation as today) and, for `wake`, ticket comments and gate-request text. Handoffs were on 0010's "never leaves" list, so this needs the `security` review named in the Status before the bounce half makes any call, shadow included. `security` may narrow it to the bounce verdict comment plus the ticket, which is enough for a label, and the ADR would then not need this extension. The existing redaction and `blocked-input` fallback (a `risk-check` secret pattern anywhere in the assembled input) apply to every point.
   - *`jg` to the provider chosen at `jg auth` (0014 decision 5):* eligible source under the search root. 0014's wrapper adds `--exclude '.scratch/'`, but `.scratch/` is tracked (only `*.lock` is gitignored), so an **ad hoc** `jg` call by a cell, which qa specify already makes and scout would make under 0014 decision 4, is not excluded and can send tickets, handoffs and `usage.jsonl` to that provider. That contradicts 0010's "board never leaves" if jg's provider is treated the same. `security` should decide whether cells must pass the exclusion (a wrapper, a `.jgignore`-style file if jg supports one, or a genome line) or whether the board may go to jg's provider.
   - *Consistency rule:* one denied-path list and one secret rule, owned in code once. Where `find` was to use an allowlist (`docs/`, `.scratch/`, `CONTEXT.md`, `apps/`, `scripts/`, `packages/`) and drop secret-matching chunks, `jg`'s wrapper uses ignore-file filtering and refuses the whole run on a secret in the root. If find is ever built, it reuses the same list and rule as the jg wrapper, or the difference is recorded with a reason. Diffs and transcripts stay out until `security` reviews them.

9. **`find` (S5) versus `jg` (0014): a recommendation, not a decision.** Recommendation: **do not build `find` as specified; keep S5 blocked on the jg trial result (0014 decision 8) and, if jg's verdict is go, drop it or re-scope it to the uncovered gap below.**
   - *What jg already covers.* Ranked files and verbatim excerpts for a repo-wide question at dispatch, one call per ticket, reused by every hop, spend on the provider account outside the $0.50 cap. Scout's "called first by scout" use is 0014 decision 4 (a pull line for scout). Cells can also call `jg` themselves at any time, and do (qa specify 3 of 3 tickets, no rule), so a mid-session lookup is partly covered too, though developer used it only 1 of 3 times.
   - *What is left.* (a) A lookup inside one already-known large file mid-session, where a grep keyword fails. (b) Text jg's wrapper excludes on purpose, the board (`.scratch/`). (b) is a reason for care, not for find: the board is the text 0010 keeps off the wire, and decision 8 asks `security` to decide it. That leaves (a), which grep and offset reads already serve at low cost.
   - *Evidence that would decide it.* From the jg trial's transcripts (phase 2, and phase 1 replay for retrieval quality): per cell run, count Read/Grep/Glob calls and tokens **after** the start-here context file was read, split into lookups inside a single file of at least 400 lines (find's case) and lookups elsewhere (jg's miss). Proposal, for the user's approval: re-scope S5 to case (a) only if in-file lookups exceed 20% of a cell's tokens above the roughly 25k floor on at least half the runs, and jg's phase 1 median recall is at least 0.6 (jg is finding files, so the remaining cost is inside them). If instead the cost is in files jg did not list, that is a jg quality problem and find would not help. If jg is no-go, S5's case is re-argued from scratch, not unblocked automatically. Three tickets cannot show significance, so the counts are judged with the spread, as 0014 says.
   - *Consequences of dropping it.* The $0.15 find cap and its slice-2 reserved budget are moot; reserved budget stays for `tier`, `verify`, `route`. Slice 8's blocker ("S5 shadow results") needs a new one (decision 10).

11. **Test seam.** As in 0010's Consequences: the highest seam is each point's public function with an injected `transport` and a temp `usage.jsonl`, so `jev.mjs` and `jev-report.mjs` are tested through it. Ordering, aging, budget arithmetic, state-machine exclusions and gate conditions get plain unit tests. Model labels get only "outside the set becomes `other`" tests. No new seam is added.

**Considered options.**
- *Build `find` now as a second retrieval path.* Rejected for now: it duplicates jg's job with a second exposure surface and a second cap, on a repo where cells already reach for jg unprompted. It stays possible if the trial shows the in-file gap.
- *A separate script or cell per point.* Rejected for 0010's reasons (copies cap, redaction, fallback, logging; a cell spends Claude tokens to save Claude tokens).
- *Let Jev fill missing Priority lines and order the frontier itself.* Rejected for v1: an explicit line always wins and aging stays code. Fills need 20 accepted fills first.
- *Let Jev suppress wakes freely.* Rejected: `informational` is only offered on inputs code has no rule for, and user, scope and verdict comments always wake.
- *A daemon or timer for the wake-up gate.* Rejected for v1: no background process until shadow shows a value.

**Consequences.**
- Each point adds `kind:"jev"` rows with its own `point` value; the genome line listing `usage.jsonl` kinds needs no new kind, but the orchestrator genome must learn to run the points when each goes live (`.claude/` work, the user's permission, per point).
- `jev-report.mjs` is extended, not rebuilt: agreement per label for route, and pass/fail lines for the priority and scope bars. The route and wake-up bars above become pass/fail lines once the user approves them.
- Nothing is built by this ADR. Ticketing follows the spec's slice list, with S5's blocker changed to the jg trial verdict, and S8's blocker as in decision 10.

*Why.* The order is the orchestrator's own pick; `rankFrontier` ran in shadow only and the aging bump was never coded. Nothing checks a ticket when it is filed, so P values are arbitrary and pipeline tickets pile up (organism-infra: 12 ready, 68 parked on 2026-10-12). ADR 0019 decision 8 already states the guardrails (one active feature, every ticket names what it serves, pipeline tickets only on a third repeat) but nothing enforces them; this amendment is that enforcement.

**The 15 decisions (settled by the user; recorded, not reopened).**
1. *Shape.* The Queue is a computed order, a pure function of each ready ticket's fields plus board state, recomputed on every read. There is no stored list.
2. *North star.* One feature is active; its ready tickets outrank all others whatever their P.
3. *Active feature.* Only the user sets it, with one command that writes one config row. Exactly one. The orchestrator may propose a switch, never make it.
4. *Urgent lane.* Only P0 jumps the active feature, and only for: `main` red, the relay cannot run, or security found a high or critical. The board refuses P0 without one of those named. P1-P3 never cross the active-feature line.
5. *Order within a tier* (inside the active feature; separately among the rest): unblock count (most first), then the P line, then the lowest ticket number. Scope is not used.
6. *Admission gate.* A ticket is ready only with a `Serves` line naming a real step of the active feature's spec or an existing incident, and a class (product or pipeline); a pipeline ticket also needs three incidents. A failing ticket is parked with the reason.
7. *Gate judge.* Code checks form and that references exist; it does not judge meaning; no model call. The user can admit a refused ticket with a logged reason.
8. *Idle fill.* With nothing ready in the active feature, the orchestrator proposes the top gated ticket of the rest. The user still approves each dispatch. Being picked resets that ticket's decay count.
9. *Decay.* A ready ticket outside the active feature, not picked while 5 tickets resolve, is parked with the reason. Unpark restarts the count. Active-feature tickets never decay. Replaces the aging bump.
10. *Unplanned tickets.* Each feature records which tickets came from its approved spec; later ones are unplanned. The Queue shows the count per feature. Past a third of the planned count, admitting another needs the user's yes. Security findings of medium or above still enter, and count.
11. *Go-live.* Applied from the start, no shadow. The orchestrator must propose the top ticket; a deviation states why, the user decides, and it is logged.
12. *Visibility.* One read-only board command prints the order, one reason per line (tier, unblock count, P, decay count left), and the parked-by-gate list. The orchestrator pastes its top lines at each dispatch proposal. The Den kanban is a later ticket.
13. *Day one.* The gate runs once over every ready ticket; the user sees the failures before anything is parked and can admit exceptions.
14. *Term.* **Queue** (CONTEXT.md): the frontier in its computed order, active feature first. The board stays the board; the frontier stays the unordered set.
15. *Timing.* Built before agent-os/03 continues.

**The four open points, one answer each.**

*A. Where class and "planned" are recorded.* **On the ticket, as header lines, written by `board create`, not on the feature.** `**Class:** product|pipeline` and `**Origin:** spec|added`. Reason: the gate and the order read tickets already (Priority, Blocked by, Serves are the same kind of line); a feature-level class fails on this board, where `organism-infra` holds product-shaped Jev tickets and pipeline tickets under one folder with several umbrella specs, and spec headers are not uniform (some have `**Status:**`, some a bare `Status:`). One source, one parser, visible in review. `board create` takes `--class` (required) and `--origin` (`spec` only when filed through the approved to-tickets breakdown; the default is `added`). *Planned* for a feature is the count of its tickets with `Origin: spec`, plus every ticket with no `Origin` line (grandfathered: all 349 existing tickets are treated as planned, otherwise day one reads as pure creep). A feature with no spec has no `Origin: spec` ticket, so its Serves can only name an incident, and the one-third cap applies only once a feature has at least 3 planned tickets (below that there is no baseline, so the Queue shows the count and does not refuse). Existing tickets have no `Class` line (0 of 349 on 2026-10-12): the day-one run (decision 13) proposes one per feature (`organism-infra`, `ci-cd`, `pipeline-telemetry`, `mods-trial` pipeline; the rest product), writes nothing until the user's yes, and the user edits the list first. Machine form of `Serves` (the gate parses this; prose after it is free): `spec:<feature> "<heading text>"` (the file `.scratch/<feature>/spec.md` exists and has a heading line containing the text, case-insensitive, and for a non-pipeline ticket `<feature>` must be the active feature), `incident:<ts>[, incident:<ts>...]` (each `ts` is a `kind:"incident"` row of `usage.jsonl`; a pipeline ticket needs three distinct rows with the same `tool`, which is a mechanical stand-in for "same cause"), or `finding:<ref>` (that ticket exists and carries a security comment; the ticket also carries `**Severity:** medium|high|critical`, and form is all the gate checks). Today's `Serves` lines are free text (128 of 349 tickets have one; all 13 ready tickets do), so existing ones fail the form check until rewritten; day one lists them.
*One conflict with ADR 0019 decision 8, for the user.* Decision 8 allows a pipeline ticket "on a third repeat incident **or when it blocks the active feature**". The spec's decision 6 keeps only the incidents. Recommendation: keep both, code-checkable: a pipeline ticket also passes if some ticket of the active feature lists it in `Blocked by`. Without this, a missing tool the active feature needs cannot be filed.

*B. Where the active-feature row lives, and whether the command can refuse a non-user caller.* **Row: a `kind:"config"` line in `.scratch/usage.jsonl`**, `{"kind":"config","ts","queue_active":"<feature>","by":"user","reason":"..."}`, the last one wins, appended through the board service's existing `appendUsageLine`. Reason: config rows already live there (Jev use cases, loop config), the board service owns one locked append, and `events.jsonl` is per-ticket (`feature`, `ticket`, `op`) with the Den subscribing to it, so a featureless row would be noise there. A dedicated `.scratch/active-feature.json` was considered: simpler to read, but a second state file with no history and no precedent; rejected. **It cannot refuse a non-user caller by identity, and the ADR should not claim it does.** ADR 0008 decision 7: the `board` CLI has no auth and whoever can run a shell can write the files. The environment markers do not help: the `CLAUDE_CODE_AGENT` value inside this architect cell read `orchestrator`, inherited from the parent. What is possible, in layers: (1) a separate entry point `scripts/queue-admin.mjs` (`active <feature>`, `admit <ref>`), not a `board` subcommand, because `npm run board:*` is on the allow list and a deny rule on `board active` would be bypassed by `node apps/organism-infra/board.mjs`; (2) it prompts on stdin and acts only on an exact `y`, as `apply-gated` does, so a Bash tool call with no input skips; (3) deny rules `Bash(npm run queue-admin:*)` and `Bash(node scripts/queue-admin.mjs:*)` in `.claude/settings.json` (a gated patch) so the permission system refuses an agent's call while the user's own `!npm run queue-admin ...` is not an agent tool call; (4) each row names `by:"user"` and the prompt shows old and new value. This covers the threat model of ADR 0021 (agent mistakes and hostile content an agent reads), not an agent that hand-appends a row; a hand-appended row is visible in `git diff` of `usage.jsonl` and the Queue prints the active row's `ts`. The proper channel is the Den: the bridge as kernel (ADR 0021 decision 7) holds the policy, so a later `POST` from the UI replaces the terminal prompt; that is the follow-up, not v1. `admit` (decision 7) uses the same entry point and writes `{"kind":"queue-admit","ts","ref","reason","by":"user"}`; the gate skips an admitted ticket.

*C. Whether the order moves out of `scripts/jev.mjs`, and what happens to `jev-order` rows.* **Yes, to a new module in `apps/organism-infra/`, behind `board queue`.** Deletion test: the order needs ticket status, locks, `Blocked by`, the active-feature row, resolved rows and events (all board state), and no model, cap, redaction or transport, which is everything `jev.mjs` exists for; leaving it there keeps a Jev point that no longer calls Jev. The interface is two pure functions over a snapshot, one reader, and the CLI is a thin adapter: `buildQueue(snapshot) -> { ordered: [{ref, tier, unblock, p, decayLeft, why}], gated: [{ref, reasons[]}], expired: [ref], unplanned: {feature: {planned, added}} }`, `checkAdmission(ticket, snapshot) -> {ok, reasons[]}`, and `loadSnapshot(root)` (the one place that reads the board; `jev.mjs frontierTickets`, `scripts/queue.mjs loadBoard` and `scripts/north-star.mjs loadBoard` are three copies of it today, and only the first is retired here). Writes stay in separate commands: `board gate [--apply]` (dry run by default; parks failures and expired tickets via the existing park path, reason naming the rule, author orchestrator), `board pick <ref> [--deviation "<why>"]` (appends `{"kind":"queue-pick","ts","top","picked","deviation"}`; also the decay reset), and `board create` stamps the lines in A. **Retired:** `rankFrontier`, `orderRow` and the `order` CLI point in `jev.mjs`, `scripts/jev-order.test.mjs`, the order half of `scripts/jev-scope.test.mjs` if it tests it, the aging bump in `apps/organism-infra/priority.mjs` `orderFrontier`, and the Frontier paragraph of `docs/agents/issue-tracker.md`. **`scripts/queue.mjs`** (the `/queue` kanban, ticket 212) reads the latest `jev-order` row for its `proposed` list; it switches to `buildQueue` so the kanban shows the computed order. **`jev-order` rows** already in `usage.jsonl` stay as history (the file is append-only); nothing reads them after the switch, and `jev.mjs priority-verdict` rows, which the flagging bar needs, are untouched. Scope labels stay displayed suggestions (Amendment 2) and leave the order, per decision 5. Test seam: `buildQueue` and `checkAdmission` are the highest seam and take a plain snapshot object, so tests build it from literals with no filesystem; `loadSnapshot` and the CLI get a temp-board test through `board-fixture.mjs`.

*D. The orchestrator genome changes (loop steps 5 and 6).* Gated `.claude/` edits; the exact diff is in the handoff `.scratch/queue/handoffs/01-architect.md`, for the orchestrator to write to `.scratch/_handoffs/gated/` once the commands exist. In short: step 5 runs `board gate` (dry run) then `board queue` instead of `jev.mjs order`; step 6 pastes the top lines of `board queue`, proposes the top ticket, states any deviation and why, asks the user, and logs the pick with `board pick`; when the top ticket is outside the active feature it says "idle fill". The `jev.mjs order` instruction and the `jev-order` row note leave the role file.

**Conflicts checked.**
- *ADR 0019 decision 8 and its Amendment 1.* Decision 8 is one active feature; Amendment 1 relaxed it to two (`den-v1` and `den-layout`); ADR 0021 lists decision 8 as amended. Spec decision 3 says exactly one. This amendment sets one: the user's `active` row is a single feature and `den-layout` tickets compete in the rest, or the user picks which of the two is active. The user decides; I did not read ADR 0021's text on decision 8 line by line, so the final wording of the supersession needs that read before accept.
- *ADR 0019 decision 8, pipeline tickets "or when it blocks the active feature".* See A: the spec narrows it; recommendation above.
- *ADR 0008 decision 7 (no auth).* See B: the user-only command is a convention plus permission rule, not an identity check.
- *Priority P0 refusal.* `board create` is the only board code that writes a Priority line, so it refuses `--priority P0` without `--p0-reason main-red|relay-down|security-high` and stores `**P0-reason:**`; the gate also fails a P0 ticket without it (a hand-edited ticket).

**Consequences.**
- New files in `apps/organism-infra/` (the order module, `board gate`, `board queue`, `board pick`, `board create` flags) and `scripts/queue-admin.mjs`. Retired code listed in C. No new dependency.
- Existing `board` tests stay; `park` and `unpark` are reused as they are.
- `security` reviews the gate (it reads `spec:<feature>` paths named by ticket text, so the feature allowlist `^[a-z0-9-]+$` of ADR 0008 decision 6 applies, and it parks tickets) and the user-only command boundary.
- Decay count = `kind:"resolved"` rows in `usage.jsonl` after the ticket's `readySince` (its last create, unpark, reopen or release-to-ready event) or its last `queue-pick` row, whichever is later; the Queue shows 5 minus that count. A ticket parked by decay returns only through `board unpark`, which restarts the count.
