# The UI steers live cells through the bridge: SSE down, authenticated POST up, a `CellRuntime` adapter whose Claude implementation runs headless stream-json child processes the bridge owns, with a three-slice path from "dispatch, watch, approve, kill" to full steering

## Interface amendment: canonical runtime and native sessions

Approved by the user in the Codex residents plan (codex-residents/01). Run views and persisted spawn records carry canonical runtime/project and validated `runtimeSessionId`; clients address bridge run IDs. An unavailable configured runtime is refused without fallback. Every launch receives a new bridge `runId` for its resource group; resumed conversations preserve both the bridge UUID and acknowledged native session. Runtime identity is recorded before launch success is returned. This amendment enables injected adapters only; production Codex execution remains gated on separate real-launch conformance.

**Decision.**

### 1. Transport: the bridge grows in place; SSE down, POST up

The UI talks to the existing bridge process over its existing localhost HTTP surface. There is no separate daemon process and no second port. ADR 0011 said the daemon would later replace `apps/bridge` behind the same surface; this decision makes that literal: `apps/bridge` gains a `cells/` module and stays the one process the user starts. `organism-infra/03` (board IPC) stays parked under ADR 0008 decision 5; this ADR does not revive it.

- **Down (cell state to the UI):** the same SSE stream (`GET /events`). New additive snapshot keys and `change` types (decision 4). Sub-second delivery needs no polling: a cell event reaches the stream as soon as the child's stdout line is parsed.
- **Up (commands to the daemon):** `POST` JSON routes (decision 3), each one command, each answered with 200/201 or a 4xx that names the refusal.

Why not a WebSocket: the traffic is low-rate commands up and a firehose down, which SSE plus POST already model. A WebSocket handshake is not covered by CORS, so it would need its own Origin enforcement, and framing needs a dependency (`ws`) or hand-rolled code. SSE plus POST reuses ADR 0011's tested hardening (Host check, Content-Type, Origin, body caps, SSE back-pressure destroy) unchanged and adds no dependency. Why not a named pipe or Unix socket: a browser cannot open one (ADR 0008 decision 8). Why not a second "daemon" port: it would double the exposure surface for no capability.

### 2. How a steering command reaches a live cell: `CellRuntime` (refines ADR 0004)

One module interface, `apps/bridge/cells/runtime.mjs`. ADR 0004's verbs, made concrete: a runtime spawns a **cell process**, and each live cell is one such object, so the interface stays small and the host owns the handle map. A capability set lets a runtime say what it cannot do (the lowest-common-denominator rule):

```
CellRuntime = {
  id: "claude",
  capabilities: { spawn, stop, approve, send, handover },     // booleans; the UI greys out what is false
  spawn({ role, mode?, ref, cwd, prompt, model?, sessionId, resume? }) -> Promise<CellProcess>,
  resumeCommand(sessionId) -> string                 // what the UI shows once an agent has ended; the bridge never runs it
}
CellProcess = {
  handle,                                            // opaque string; key in the host's map
  events: AsyncIterable<CellEvent>,                  // tool start/end, message, usage, permission-request, state, done; ends when the process exits
  closeInput() -> void,                              // ends the child's stdin; idempotent
  signal(sig: "SIGTERM" | "SIGKILL") -> void,        // synchronous (the exit handler cannot await); the adapter chooses child or process group (S4b)
  exited: Promise<{ code, signal }>,                 // resolves once when the child has exited; never rejects
  send?(text) -> Promise<void>,
  decide?(requestId, { allow, reason? }) -> Promise<void>   // answers a held permission request
}
```

*(Amended, architect, 2026-10-05, after the qa specify of organism-infra/140.)* The first draft had one `stop() -> Promise<void>` on the process. That cannot serve the kill row below: the host owns the grace periods (`KILL_GRACE_MS` in `cells/policy.mjs`) and the order of steps, the shutdown handler must send SIGKILL synchronously from the `exit` event, and `terminated` is set only once the host has seen `exited`. So the process exposes the three primitives (`closeInput`, `signal`, `exited`) and the host composes the escalation; no adapter implements its own. `signal` accepts only the two named signals, and the adapter's `signal` is where a process-group kill (S4b) lives, so decision 6.9 holds (a signal goes only to a process the bridge spawned this run). `resumeCommand` moved from the process to the runtime so the host can fill `resume` for a replayed agent that has no process, and so no `claude --resume` string is composed outside the adapter (the "nothing outside `claude-adapter.mjs` names a Claude flag" rule). With no runtime, `resume` is `null`. *Names:* `role` replaces `cellType` here and below, per ADR 0019 decision 10 (see "Names as built" under decision 3).

The adapter builds the child's environment itself (an allowlist, decision 6.6), so it is not a parameter. `startBridge({ root, port, uiDir, auth, runtime, policy })` takes the runtime as a parameter. **Until the adapter ticket (D2) lands there is no default: a bridge started without a runtime answers `POST /agents` with 503 and spawns nothing; D2 makes the Claude adapter the production default.** Tests pass a fake runtime. Two adapters (Claude, fake) make this a real seam. `policy` is a test-only override of the constants in `cells/policy.mjs` (`maxConcurrent`, `sessionCap`, `killGraceMs`); the production entry point passes none, as with `auth` (decision 6.1). The 8-session cap is a hard ceiling: an override can only lower it (`min`), never raise it. `startBridge` returns `host: { start(input), shutdown() }` beside its existing fields; `start()` is the internal entry of decision 3 and is never a route.

How the **Claude adapter** carries each command (the answer to "hooks, stdin, signals"). The bridge spawns `claude` as its own child with piped stdio and holds the pipes, so the bridge opens no inbound route for a cell. (The child itself may open one: every `system/init` carries a `messaging_socket_path` under `/tmp/cc-socks`, see 6.3 and spike S8.)

| Command | Mechanism | Slice |
|---|---|---|
| Dispatch | create a worktree, then spawn `claude -p --input-format stream-json --output-format stream-json --verbose --replay-user-messages --permission-prompt-tool stdio --session-id <uuid> --agent <cell> --setting-sources project,local --strict-mcp-config --settings '<inline deny JSON>'` (the fixed template of 6.6) with cwd in it; the prompt is the first stdin user message; the bridge mints the session id | 1 |
| Watch | parse the child's stdout stream-json lines into `CellEvent`s with `parseClaudeLine` | 1 |
| Kill | close stdin, wait a bounded grace (`KILL_GRACE_MS`, 5 s, one constant in `cells/policy.mjs`), then SIGTERM, then SIGKILL after a second grace, on the `ChildProcess` the bridge itself spawned this run (the conversation is kept and `--resume` reopens it); never a pid from a file or a request. The child is spawned as a process-group leader (`detached: true`) and SIGTERM and SIGKILL go to the group, until a valid S4b re-run shows the child alone is enough (user ruling, 2026-10-08; spike S4b, below) | 1 |
| Approve or deny a tool permission | the CLI writes a `control_request` (`request.subtype == "can_use_tool"`, decoded under 6.5) on stdout; the host holds it as an approval until the UI decides, then writes the matching `control_response` on stdin. Timeout, expiry, bridge shutdown or any request the decoder does not accept answers **deny** | 1 (only if spikes S3 and S8 pass; else slice 2) |
| Message mid-task | write a user message line on the child's stdin, carrying a bridge-minted `uuid`; the child re-emits the line on stdout with `isReplay: true` and the same `uuid` once it takes it (`--replay-user-messages`), and that replay marks the message received *(amendment 12)* | 2 |
| Take over or pair | **hand over**, not pair: stop the child, then the UI shows `claude --resume <sessionId>` for the user's terminal, run in the cell's cwd. Two live processes never share a session. Live pairing is not offered | 2 |

The exact shapes of the stdin user message, the `control_request` and the `control_response` are undocumented and unverified; spikes S1 to S3 fix them before slice 1 builds. Nothing outside `cells/claude-adapter.mjs` may name a Claude flag or message shape.

**Process lifetime.** Children belong to the bridge, and the bridge ends every child it started the same way a user kill does (stdin close, grace, SIGTERM, grace, SIGKILL):
- A **shutdown handler** runs the kill sequence on every live child on `SIGINT`, `SIGTERM`, `SIGHUP` and an uncaught exception, and sends SIGKILL synchronously from the `exit` event (no await is possible there). The host sets `state: "terminated"` and writes the `sessions.jsonl` line only after it has seen the child exit, never before. *(Amended 2026-10-05, organism-infra/140.)* `startBridge` installs these handlers (the bridge is the process that owns the children, and the highest test seam is `startBridge`), but only when it was given a runtime, so a runtime-less bridge, including every existing test, touches no process-level state. The handlers run the host's `shutdown()`, which is idempotent and is the same sequence `close()` runs. A signal handler then ends the process (it must not leave the process alive by swallowing the signal); the uncaught-exception handler writes the error to stderr and exits non-zero, never a clean exit. `close()` removes every handler it installed.
- *(Amended 2026-10-10, den-v1 loop S3.)* **A finished child is ended by the host, not by itself.** The live CLI does not exit after its `result` line: with stream-json input it waits for the next user message until stdin closes (spike S3 ran two turns in one child; the stubs had exited by themselves). So when the runtime reports `done`, the host runs the same sequence as a kill (stdin close, grace, SIGTERM, grace, SIGKILL) without marking a stop: the agent ends `done` or `failed` by the `done` event's own verdict, and a stop that arrives meanwhile still ends it `terminated`. Spike `Live` (`cells/conformance-live.mjs`, `npm run smoke:live`) shows it on the real CLI, through `startBridge` and the production runtime: the agent ended `done` by itself after one held and allowed `Write`. A later slice that sends a message after a result (ticket 107) must revisit this.
- Closing stdin ends an **idle** child (spike S1). Whether it also ends a child **in the middle of a tool call**, and whether a Bash tool's own subprocesses (a dev server, `npm test`) outlive the SIGTERM, is unproved. Spike S4b was meant to settle both, but three runs have not put a tool process in flight (round 3: the `tail -f` call was refused by the CLI), so **both stay unproved and the defensive design is the design (user ruling, 2026-10-08):** the adapter spawns the child as a process-group leader (`detached: true`, so it is its own group, still holding the bridge's pipes) and signals the group (`process.kill(-pid)`) on the SIGTERM and SIGKILL steps. Only a valid S4b re-run (a tool process shown in flight, a tool pid whose parent chain is not the child, and no `permission_denied`) that finds no survivor may remove it, by a further amendment. That is still a signal to a child the bridge spawned this run, so decision 6.9 holds.
- A bridge that is itself SIGKILLed or crashes cannot run any handler. The only protection then is stdin EOF (S4b, unconfirmed: EOF may not end a child in a tool call or with a background task). On the next start the host cannot know whether a previously live child is still running (6.9 forbids reading a pid from a file), so it marks those cells `terminated` with reason `bridge-restart-unverified`, not `bridge-restart`, and the UI shows the `claude --resume` command with a note that the old process may still be alive.

Cells do not survive a bridge restart in the normal case. This is the cost of owning the pipes; it removes the pid-reconciliation and process-verification problems of a detached design.

**Background sessions are an optional later adapter mode, not part of slices 1 to 3.** `claude --bg` plus an HTTP `PermissionRequest` hook would let cells outlive the bridge, but the user cannot use it now. If adopted, it needs its own security review, because it adds an inbound hook route and a hook token. The requirements from review round 1 carry over to it: an `Origin` exemption for the hook route with a Host check, a per-session hook token (at least 128 bits) delivered by environment only, never argv or a file, with a canary spike proving the environment allowlist holds under `--bg` (a background session may take its environment from the CLI's supervisor); a 256 KB body cap; the UI token rejected on the hook route and the hook token on every UI route; and a registry-pid kill fallback only after verifying the process command line and start time.

**Billing and ADR 0001 (open question; not asserted).** Headless `claude -p` is still the unmodified CLI on the owner's login: no SDK package, no API key, no model API, so it satisfies the letter of ADR 0001. Whether it satisfies the intent (cells run on the owner's plan usage) depends on a fact nobody here has confirmed: the support article read by `scout` says `claude -p` usage has drawn from a separate monthly credit since 2026-06-15. If that is true, daemon-spawned cells would be metered apart from the interactive session, the usage guard (which reads plan usage) would not see their consumption, and ADR 0001 and ADR 0002's auto-pause would need amending. If it is false, nothing changes. This ADR neither assumes nor rules out either answer. Spike S5 measures it (a plan-usage reading before and after one trivial headless run, plus the account's usage page), and the user confirms. Until the user does, slice 1 may be built and exercised on trivial prompts, but headless dispatch is not adopted as the default way to run relays.

Fail-closed rule for every adapter: a permission request with no decision (timeout, expiry, bridge shutdown, hostile or unparseable request) is answered deny or left unanswered by a dead child. The bridge never auto-allows.

**One line parser, one source.** Transcript lines and stream-json stdout lines share the message shape (`message.content` blocks, `message.usage`). `parseClaudeLine(line) -> CellEvent[]` is that one parser. The child's stdout feeds it directly; this keeps the user's "one reader feeds animation and cost" decision, with a pipe instead of a file. A transcript tailer (an `fs.watch` incremental read of `~/.claude/projects/<cwd>/<session>.jsonl` and its sibling subagent files) is kept as a secondary feeder, enabled only if spike S2 shows the stdout stream omits subagent activity. Pipe latency should be well under a second; unverified, S2 measures it. Permission requests arrive on the same stream and do not depend on the tailer. Cell output is untrusted text; the input rules are decision 6.8.

### 3. Routes and the `CellHost` module

Behind the routes sits one deep module, `CellHost` (`apps/bridge/cells/host.mjs`). The routes are thin; the module owns the policy, the live-cell map, the registry and the event merge.

| Route | Body | Does |
|---|---|---|
| `POST /session` | `{ code }` | redeems the one-time launch code for a session token (decision 6.2); Host, Origin, Content-Type and body cap, no Bearer |
| `POST /cells` | `{ ref, cellType, mode? }` | dispatch (below); **the only HTTP way a cell starts**; Bearer token |
| `POST /tasks` | `{ role, text }` (text at most 2 KB) | *(amendment 9)* writes a ticket under the `den` feature, then starts that role for it in direct mode; Bearer token |
| `POST /requests` | ADR 0011's Gate request body | records an audit line; runs nothing; now Bearer token and required Origin (decision 6.1) |
| `POST /cells/:id/stop` | none | kill |
| `POST /cells/:id/message` | `{ text }` (at most 2 KB) | send (slice 2); built as `POST /agents/:id/message` *(amendment 12)*, answering `202 { ok, messageId }` |
| `POST /approvals/:id` | `{ decision: "allow" \| "deny", note? }` | answer a permission request |
| `GET /approvals/:id` | none | the full tool input for a pending request, token required |

There is no inbound hook route: permission traffic rides the child's pipes, never the network.

**Dispatch policy** (all refusals write nothing and start nothing):
- **Consent is the token, not a file line.** A cell starts only from a Bearer-token `POST /cells`. The bridge never starts a cell because it saw a `dispatch-approve` line, whether that line arrived through `POST /requests` or was appended straight to `.scratch/_requests/requests.jsonl` by a process on the same account (any cell can do that). The Run button calls `POST /cells`; the bridge itself then appends the `dispatch-approve` line (with `outcome: "dispatched <cellId>"`, ADR 0011 decision 6's append-only form) as an **audit record, not proof**: a line in that file proves nothing about who wrote it.
- `ref` names a ticket in the snapshot with `gate == "dispatch"` (ADR 0011 decision 3). *(Amended 2026-10-12, organism-infra/154, user request of 2026-10-06 to reach every agent from the den: this precondition is replaced. Read the next bullet.)*
- **Who may be dispatched, and how many** *(amendment 14, organism-infra/154; replaces the line above).*
  1. **Eligibility is membership of the frontier, not the gate.** `POST /agents` accepts a `ref` that is in the snapshot's `frontier` (ready, unblocked, no claim lock) and has no live agent. Otherwise 404 for an unknown ref and 409 for any other ref (the error text says "not in the frontier" or "already has a live agent"). The user may start any frontier ticket, not only the first; priority order is advice, not a lock. `gate == "dispatch"` stays what ADR 0011 decision 3 says (amended the same day): the one prompt the den shows, which still gates the orchestrator-facing `dispatch-approve` request and nothing on this route.
  2. **One capacity rule, one place.** A pure module `apps/bridge/cells/capacity.mjs` exports `capacity({ liveRefs, lockedRefs, max, cap }) -> { max, cap, load, live, room, refs }`. `load` is the number of distinct refs that either hold a live agent in the host or hold a board claim lock; `live` is the number of host agents; `room = max(0, min(max - load, cap - live))`. `max` is `max_concurrent_cells` (default 8) and `cap` is the 8-session cap, both read from `cells/policy.mjs` (a policy override may only lower them). A relay on one ticket is one agent at a time, and a host agent that has claimed its ticket is one ref in both sets, so nothing is counted twice. Locks held by cells started outside the bridge (a terminal `claude --agent`, a desktop session) count, which is how the cap on cells at once stays true when the bridge is not the only starter. A stale lock from a dead holder counts too and costs a slot until it is reclaimed; the 429 text names the refs that fill the slots, so the user can see which.
  3. **The host takes the locks as a parameter.** `createHost` gains `lockedRefs: () => Promise<string[]>` (the bridge passes the hub snapshot's holders). `admit()` awaits it with the usage reading, before the synchronous step, then computes `capacity` and reserves in that same step, so the "one synchronous step" guarantee above holds for the host's own reservations. A claim made by an outside process between the read and the reservation can exceed the cap by one; the board's atomic claim keeps tickets exclusive regardless. All three entries (`dispatch`, `start`, `direct`) use the rule, so the cap means the same thing wherever an agent starts. `POST /tasks` is unchanged otherwise.
  4. **The snapshot reports it.** The hub adds a top-level `capacity` object (additive, schema 1) built with the same function from the same inputs, so the Run buttons and the host cannot disagree. Between snapshots the UI recomputes it with the same imported function from the agents and ticket holders it already holds, taking `max` and `cap` from the last snapshot's `capacity`; no new change-frame type is added. The UI offers a Run control on every frontier ticket, enabled only while `capacity.room > 0`, with the reason shown when it is not ("8 of 8 running: <refs>").
  5. **Roles.** The route still refuses `developer`, `qa` and `security` with 409 "dispatch the orchestrator". The UI's role choice for a ticket defaults from its type (feature or bug: `orchestrator`; design-question: `architect`; spec work: `product`; UI or asset work: `designer`) and the user may change it among `orchestrator` and the non-relay roles. A relay-hop role is never offered.
  6. **Overlap.** ADR 0002 and CLAUDE.md ask for tickets "with non-overlapping files". The route cannot check that. Every agent now runs in its own worktree (amendment 7), so overlap costs a merge conflict at PR time and never a shared working tree. The den shows the other running refs beside each Run control; judging overlap stays with the user.
  7. **Unchanged:** the token gate, the 90% usage refusal, the double-click atomicity (a test fires two dispatches at one free slot), the relay-hop 409, and the status table apart from the 409 and 429 texts above.
- **Known residual (not closed here):** the orchestrator genome (step 2) still reads `requests.jsonl` and treats a `dispatch-approve` line as the user's answer, so a prompt-injected cell can forge a line and talk the orchestrator into acting. This is the same posture as before this ADR, and no UI token defends it, because the orchestrator cannot verify who wrote a line. - `resume` is `null` while the child runs; once the cell is stopped, done or terminated it is `claude --resume <sessionId>` (a string for the user's terminal; the bridge never runs it).
- **`summary` is a display hint, never the basis of an allow.** It is capped at 200 characters, so a padded command can hide its tail past the cut. The snapshot therefore also carries `inputLength` and `truncated`, and the allow action is gated on the full input (decision 6.5): the UI must fetch `GET /approvals/:id` and render the whole input before `allow` is enabled; `deny` is always enabled.
- `state` is one of the director's `STATES` (ADR 0007): `working`, `waiting_on_user` (a permission is pending or the session is idle awaiting input), `blocked`, `done`, `failed`, `throttled`, `terminated` (killed by the user, or ended by a bridge restart), `idle`. `snapshotStateSource` (ADR 0011 decision 7) can key off it directly, so nothing new is animated.
- `change` types added: `cell` (full object, or `null` when it leaves), `approval` (full object). Same `seq` rules as ADR 0011 decision 5; unknown types stay ignored.
- `tool` and `tokens` come from the line parser. Cost-pricing and the telemetry reader are a separate ticket; this ADR only fixes that the same parser feeds them.
- Registry persistence: an append-only `.scratch/_run/sessions.jsonl` (spawn, decision, stop; one line each, with `ts`, `cellId`, `ref` and, for decisions, the request id and the acting route). *As built by 140:* events `spawn` (`agentId`, `ref`, `role`, `sessionId`, `route`), `stop` (`agentId`, `ref`, `route`) and `end` (`agentId`, `ref`, `state`, `reason?`); `route` is `POST /agents` or `POST /agents/:id/stop` on the HTTP path and `start()` for the internal entry, which is how a reviewer tells a relay-runner start from a click. On start the host replays it for history and marks cells that were live as `terminated` (decision 2, process lifetime). `.scratch/_run/` should be git-ignored; the developer adds that line to `.gitignore`. **The file is untrusted input** (any cell can write it, same account): replay validates every field (decision 6.9), drops lines that fail, and nothing read from it is ever signalled or executed.

### 6. Auth and exposure (`security` reviews this section)

Threat model, in order of likelihood: (a) a web page in the user's browser firing requests at localhost (CSRF, DNS rebinding); (b) **a cell itself** (an agent, possibly prompt-injected) running `curl` against the bridge, or writing files on the same account, to approve its own permission request, dispatch, or kill another cell; (c) another local OS user on a shared machine; (d) malformed or hostile cell output (stdout or transcript lines).

The principle that follows from (b): **the UI token is the only proof of user intent.** A file line, a snapshot id or an unauthenticated request proves nothing, because a cell can produce all three.

1. **Bind, Host, Origin, preflight.** Loopback `127.0.0.1` only, not configurable (ADR 0011). Every route keeps the Host check. Every mutating route (`POST /cells`, `POST /cells/:id/stop`, `POST /cells/:id/message`, `POST /approvals/:id`, **and `POST /requests`**) additionally **requires** an `Origin` header equal to `http://127.0.0.1:<port>` or `http://localhost:<port>` (a browser always sends one on a cross-site POST; ADR 0011 only checked it when present), `Content-Type: application/json`, a valid Bearer token (item 2), and the 4 KB body cap. `GET /approvals/:id` needs the token too. Failures return 403 or 401 and write nothing. There is no exemption and no hook route: permission traffic never crosses the network (item 3). `OPTIONS` on any mutating route returns no `Access-Control-Allow-*` header. If the Vite dev origin is ever allowed, it is one exact allowlist entry, never a pattern. Tests assert each of these. *(Round 2, F7:)*
   - **One route registry, default deny.** Every route is a row in one table (`cells/routes.mjs` or the bridge's equivalent): method, path pattern, `auth` (`none` for the unauthenticated reads, `origin` for `POST /session`, `token` for the rest) and `mutating`. The router serves only registered rows; anything else is 404 with no side effect. The auth tests are table-driven from that registry and enumerate it, so a route that is added or renamed (ADR 0019 decision 10: `/cells` becomes `/agents`) is covered by default, and a mutating row missing from the auth tests fails the suite.
   - **Auth runs first.** Host, Origin, Content-Type, body cap and Bearer are all checked before any route parameter, ticket ref, cell id or approval id is looked up, so an unauthenticated caller gets 403 or 401 and never a 404 or 409 that confirms a ticket, cell or approval exists. A test sends each mutating route with a real and a bogus id and no token and asserts identical responses.
   - **Note (amendment 5, organism-infra/141):** `GET /approvals/:id` is a token-gated *read*, so it skips the Content-Type check (there is no body) and checks `Origin` only when one is present (a browser sends none on a same-origin GET). Host and the Bearer token are still required, and auth still runs before the id is looked up. Every mutating route keeps the required Origin.
   - **Nothing disables or presets the token.** No environment variable, CLI flag, config file or request field turns the check off or supplies the token or launch code. Tests inject them only through a `startBridge` option (`auth: { launchCode, ttlMs, now }`); the production entry point passes none.
2. **One-time launch code, then a per-run session token** *(round 2, F2: the fragment URL lands in the browser's history database and, if an agent's tool call ever starts the bridge, in a transcript under `~/.claude/projects`, both readable by any cell on the account; so the printed secret must be worthless once used)*. At start the bridge generates a **launch code** (32 random bytes) and prints one launch URL with the code in the fragment: `http://127.0.0.1:4317/#code=<...>`. The code is **one-time and short-lived**: it expires after `LAUNCH_CODE_TTL_MS` (5 minutes, one constant) and is burned on its first successful redemption; five failed redemptions also burn it. The UI reads the fragment, removes it from the address bar, and sends `POST /session` with `{ code }` (Host, Origin, Content-Type and body-cap checks; no Bearer, since none exists yet). The bridge answers with a **session token** (32 random bytes, in the response body only) and keeps up to four live session tokens **in memory only** (not on disk, not in the environment of anything it spawns); all die with the bridge. The UI keeps the token in `sessionStorage` (decision 7, reload) and sends `Authorization: Bearer <token>` on every route in item 1. A leftover URL in history or a transcript is therefore inert: the code is spent or expired. A reload keeps the session through the stored token (decision 7, reload); how the user gets a new launch code without restarting the bridge is part of "How the bridge is started" (decision 7), which is still open. The token is accepted **only** in the `Authorization` header, never a query string, and never appears in a log line, an error body or the snapshot; the code is likewise never logged. The printed URL goes to the bridge's own console only: never in argv (for example to `open <url>`, which `ps` shows), never written to a log or file. **The user starts the bridge, never an agent's tool call** (decision 7), because a code printed into a cell's transcript is readable by any cell until it is spent or expires; the window is five minutes and ends at the user's first click. A custom header also forces a CORS preflight the bridge never answers, which stops cross-origin scripts even if the Origin check had a hole. The comparison hashes both sides with sha256 and uses `crypto.timingSafeEqual` on the digests (the raw call throws on unequal lengths); any failure, including a malformed header, returns 401, never 500. Why not write the token or code to a file: a cell runs as the same OS user and can read any 0600 file the user can, which defeats threat (b). A cell also cannot find it in the bridge's environment because there is none. **Residual, stated plainly:** a cell that reads the launch code from a transcript or the history database in the window before the user's click can redeem it first and hold a session token. The window is bounded and the user's own click then fails visibly ("code already used"), which is the signal to restart the bridge. **Scope, said plainly:** the token gates the bridge, not the operating system. A process on the same account can still signal another process it can see; this ADR does not close that.
3. **The bridge opens no inbound permission route; the channel is the child's pipes, but the child's own socket is unverified (F1).** The bridge adds no hook route and no hook token, and a cell cannot submit a permission request or a decision through any route of the bridge. A cell can only write to its own stdout, which the bridge treats as untrusted text (item 8). A permission request gets a bridge-minted approval id bound to that child. **The claim "no other process can answer it" is withdrawn; spike S8 (round 3) ended in outcome (c), accepted by the user on 2026-10-08 with the conditions below, and the claim is restated as "not shown to answer a permission request with the one shape tried".** Every `system/init` in the S1 and S3 fixtures carries `messaging_socket_path: /tmp/cc-socks/<pid>.sock` and `capabilities` including `interrupt_send_now_v1` and `msg_lifecycle_v1`: the child itself listens on a pid-named Unix socket. If that socket accepts user messages, interrupts or a `control_response` from any local process, then another cell could inject text into a running agent or answer its permission request, and holding the stdin pipe proves nothing. S8 measures it (decision 7). Outcomes: (a) the socket is absent or disabled by a flag or environment variable that only narrows the child (allowed; the adapter sets it, and 6.6's test asserts it); (b) the socket exists but accepts neither messages, interrupts nor responses and streams no events: go; (c) it accepts messages or interrupts but not a `control_response`: the approval hold stands, the injection residual is written into this item and goes to the user for acceptance before the adapter builds; (d) it accepts a `control_response`, or leaks the request ids and inputs: **slice 1 ships without the approval inbox** (the fail-closed path in decision 3, Permissions) and the approval design is reopened, because the hold would not bind. The adapter is not built until S8 has a recorded verdict. The remaining text of this item holds only under outcomes (a) to (c). **Accepted residual, outcome (c) (user, 2026-10-08; `security` conditions (a) to (c)).** Any process running as the account's uid can write a text message into a running child through its `/tmp/cc-socks/<pid>.sock` (spike S8: the message reached the model, queued until the running tool call ended, and the model treated it as a "peer session" message). Every cell child has Bash and the same uid, so a prompt-injected cell could enumerate the directory and inject text into a sibling cell's session: cross-cell lateral movement, bounded by the target's auto-allowed tools, not new host compromise. The model's reply that it had "nothing to act on" is model behaviour, not a control. What was tried against the approval hold: one `control_response` shape (`success` with `behavior: allow`, the real `request_id` and the full `updatedInput`); the file was not written and the stdin deny took effect. This shows the hold binds **for that shape only**, not that no shape can answer. Conditions: **(a)** the claim is "not shown to answer a permission request with the one shape tried", never "cannot"; outcome (d) is not ruled out for good, and a second-shape `control_response` probe is a **gate on any later widening** of what a cell may do unattended (more auto-allowed tools, a lighter approval hold), not only a follow-up; **(b)** this paragraph is the "written into this item" the outcome requires, and it is the amendment 6 record; **(c)** detection to consider in 143 (not tested): in the S8 fixture the injected message shows on stdout as `command_lifecycle` (started and completed) with a `command_uuid`. In slice 1 the host sends no mid-turn messages, so an unexpected `command_lifecycle` is a signal to surface (and may be a deny-all trigger), but only after a probe for an injection while idle shows the same signal. The host's startup notes record the residual. The bridge never touches `/tmp/cc-socks` itself. The design still removes the hook-route, hook-token and `--bg` environment-delivery findings (M1, M2) for slices 1 to 3. The child's environment is an allowlist the bridge builds (item 6), and since the bridge spawns the child directly there is no supervisor to widen it; spike S1 plants a canary variable in the bridge's environment and checks it does not reach the child, and checks that the owner's login works with the allowlist alone. If login needs another variable, adding it is an ADR amendment, never a silent change, and an API key is never added (ADR 0001).
4. **Reads stay as ADR 0011 left them** (`/state`, `/events`, `/metrics` unauthenticated on loopback), with one narrowing: the snapshot carries only a tool name, a 200-character summary with secret-pattern matches masked (reuse the risk-check patterns), `inputLength` and `truncated`; *(round 2, F7)* the same mask and the same control and bidirectional-override escaping apply to **every** string a cell can influence that reaches the snapshot or the SSE stream: `approvals[].summary`, `cells[].tool.summary` (a running Bash tool's summary can hold a token), and the `note` and `reason` text of decisions and sessions lines; the full tool input is served only by the token-authenticated `GET /approvals/:id`. Residual risk, stated plainly: any local process or user can read the snapshot, including handoff text, cell ids and session ids (and so the `claude --resume` string), as today. This design assumes a single-user machine. *(Amendment 10, den-v1 loop S2:)* **Transcript.** The stream and the snapshot now also carry each bridge-run agent's transcript, which widens what a local reader of these unauthenticated routes can see: the agent's own text, each tool call's name and 200-character summary, a clipped tool **result**, and each permission request's tool name and outcome. The frame is `{ seq, type: "transcript", agentId, entry }` with `entry.kind` one of `message`, `tool`, `permission`, `ended`; `entry.id` numbers an agent's entries, and a frame that repeats an id replaces that entry (a tool gets its result, a request its answer). The snapshot's `transcripts` holds the last 100 entries of at most 4 agents, so a reloaded page can refill its panel. The rule above holds for every string in an entry: secret-pattern matches are masked span by span, control and bidirectional characters are shown as escapes (newlines and tabs stay), and text is capped (4,000 characters a message, 2,000 a tool result, with the dropped count stated). **A tool's input is never in an entry**; `GET /approvals/:id` stays the only place it is served. The mask is pattern-based, so a secret of a shape the patterns do not know (the contents of a file the agent read, say) can reach the stream in a tool result; the same text is already in the session file on disk, readable by any process on the account.

   **Result and cost.** Each agent in the snapshot and in `agent` frames also carries `model`, `usage` (`{ input, cacheWrite, cacheRead, output, final }`), `costUsd`, `reply` and `durationMs`. While the agent runs, `usage` is the host's running total by tier, counting each message once; its output count is partial (`final: false`). When the runtime reports done with its own totals, those replace the running count (`final: true`), and `costUsd` is the runtime's figure exactly as reported (for Claude, the result line's `total_cost_usd`); the bridge computes no cost of its own. `reply` is the first 280 characters of the final reply, on one line, masked and escaped by the rule above; it is the one new piece of cell text on the agent row. `durationMs` is spawn to exit on the bridge's clock. All of it is cell output, so each value is kept only if it is a plain value in range (a model id of at most 64 characters from a fixed alphabet, whole non-negative counts, a cost between 0 and 100,000), and a value that fails is dropped on its own. The `end` line in `sessions.jsonl` carries `model`, `usage`, `costUsd`, `durationMs`, `cliMs` and `turns`, never the reply; replay reads the first four back under the same checks (decision 6.9). After the end line the bridge appends one `kind:"cell"` row to `.scratch/usage.jsonl` (ADR 0008 decision 12) through the same symlink-refusing append `log-cell.mjs` uses: `{ kind, ts, ticket, cell, mode?, model?, tokens, ms, outcome, input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens, cost_usd, cli_ms?, turns?, source: "bridge", agent, tokens_partial? }`. `tokens` is the four tiers summed, which is larger than the Agent-tool total a relay row records; `tokens_partial: true` marks a run that ended without reporting its own totals, and `cost_usd` is then `null`. Every field of the row comes from the host's own record, so no cell text reaches the ledger. A failed ledger write is logged and changes nothing else. This is the bridge's one write to `usage.jsonl`.

   **A message to a running agent** *(amendment 12, den-v1 loop S5)*. `POST /agents/:id/message { text }` is token-gated like every mutating route. The host trims the text and refuses it (400) if it is not a string, is empty, is over `MESSAGE_MAX_BYTES` (2048 UTF-8 bytes) or matches a secret pattern; it refuses (409) an agent that has ended, is being stopped, has reported done and is being closed, or whose runtime has no `send` capability, and (429) an agent that already has `MESSAGE_QUEUE_MAX` (8) messages it has not taken. An accepted message gets a bridge-minted UUID, is written once to that agent's stdin as typed (JSON-encoded, one line), and is answered `202 { ok: true, messageId }`; a failed write is a 502. This is the one place a client string reaches a cell without passing through a ticket file: it reaches the child's stdin as a user message, never argv and never the prompt template, and only for an agent the caller names by id with a valid token. The audit line in `sessions.jsonl` is `{ event: "message", agentId, ref, messageId, bytes, route }`: the size, never the text. The transcript shows the message as an entry `{ kind: "message", role: "user", text, messageId, status }`, its text cleaned and capped like cell output, on the same unauthenticated stream as the rest of the transcript; `status` is `queued` once written, `applied` when the runtime reports the child took it, and `undelivered` if the write failed or the agent ended first, each change resent under the entry's id. **How "taken" is known.** The runtime emits `{ type: "message-applied", id }` when the child's stdout carries a `user` line with `isReplay: true` whose `uuid` is one this process wrote and has not yet seen replayed; the prompt's own replay (an id the CLI mints) and any id the process never wrote are dropped, so cell output cannot mark a message that was not sent. Recorded live (CLI 2.1.293, haiku, 2026-10-10, `fixtures/live-message*.jsonl`): a message written while a `Write` request was held was replayed with its `uuid` after that tool's result, joined the running turn (one result line), and the final reply followed it; the same run shows `command_lifecycle` lines (`queued`, `started`, `completed`) and echoed `control_response` lines on stdout, which the parser reads as nothing. **The end of the work.** A `done` that arrives while a message is still `queued` does not close the child: the message will be taken as a further turn, and that turn's `done` ends the agent. If no replay comes within `MESSAGE_SETTLE_MS` (15 s) the host closes the child anyway and the message ends `undelivered`. When a message is applied after a `done`, the earlier verdict and totals stop being final: the running count continues from them, and the later result line's totals replace them. Whether a later result line's `usage` and `total_cost_usd` are cumulative over the process or per turn has not been observed live (the recorded run had one result line), so the run record of an agent that took a message as a further turn is the last result line's figures, unverified as a whole-run total. Not built: cancel while queued, a per-message acknowledgement event, and the hand-over flow.
5. **Approval binding, the full-input rule, and the bare decision.**
   - An approval id is minted by the bridge, one-shot, bound to one cell and one request, and expires (default 10 minutes). A second decision on the same id returns 409. Expiry, bridge shutdown and a dead child answer deny.
   - **Allow requires the full input.** The 200-character summary can hide the dangerous tail of a padded command, so it is never the basis of an allow. The UI must fetch `GET /approvals/:id` and render the entire tool input (scrollable, never truncated) and its length before the `allow` control is enabled; `deny` is always enabled. The bridge enforces it too: `POST /approvals/:id` with `allow` returns 409 until a token-authenticated `GET /approvals/:id` has been served for that id (a test). The UI renders the input as text only, never HTML (React escaping plus ADR 0011's CSP), and shows control characters and bidirectional-override characters visibly (for example as `‮`), so they cannot reorder or hide text.
   - **The response is only ever a bare decision.** The encoder emits allow or deny with `reason` as plain text. If the protocol's allow response requires the tool input echoed back, the encoder returns the **original request input unchanged** (a test asserts deep equality), and it never emits `updatedPermissions` or any key that would persist or broaden a rule.
   - Ids for cells and approvals carry at least 64 random bits (16 hex characters; the examples above are that length).
   - **The decode contract** *(round 2, F3; the real shape from the S3 fixture, nested, not the flat shape in the 105 ticket comment)*: `{ type: "control_request", request_id, request: { subtype: "can_use_tool", tool_name, display_name, input, description, permission_suggestions: [{ type: "setMode", mode: "acceptEdits", destination: "session" }], tool_use_id } }`. `decodeControlRequest(obj)` returns an approval only when `type === "control_request"`, `request.subtype === "can_use_tool"`, `request.tool_name` is a non-empty string and `request.input` is a plain object; `request_id` must be a string of at most 128 characters and is treated as an **opaque key**, never parsed, never shown as an id: the host maps it to its own minted approval id. Anything else (another subtype, a missing or mistyped field, an array for `input`) is answered with a `control_response` of `behavior: "deny"` when a `request_id` string can be recovered, and is otherwise dropped; it is never allowed, and never reaches the UI as an approval. A second `control_request` with a `request_id` already held or already answered for that child is answered deny and creates no approval. `permission_suggestions` is **ignored** (it is the protocol's vehicle for broadening: a `setMode acceptEdits` suggestion would widen the session). The encoder emits only `behavior` (`allow` or `deny`), `reason`/`message` as plain text, and, for allow, `updatedInput` equal to the original `request.input` (S3's allow was honoured with exactly that; the deep-equality test stands). It never emits `updatedPermissions`, a mode or a rule. While the bridge holds an approval it never writes anything else about it to the child.
6. **Spawn safety.** Spawn with `spawn` and `shell: false`, never a shell string; the worktree is created with `execFile`. The child's environment is an allowlist (PATH, HOME, locale, `DEN_CLAUDE_BIN` if set), not a copy of the bridge's. The binary comes from `DEN_CLAUDE_BIN` or `claude` on PATH, never from a request. Worktree paths and branch names are derived server-side from validated `ref` and `cellType`; `ref` segments never start with `-`. Kill and message act only on cells in the host's live map, by `cellId`. No secret goes in argv. *(Round 2, F4:)* **The argument builder is a fixed template.** `buildClaudeArgs({ sessionId, agent, model? })` returns a list whose every element is either a literal flag or one of those three validated values (UUID pattern; role from the allowlist; model from a fixed list), plus the inline `--settings` JSON from 6.10. It has no `extraArgs`, `allowedTools` or other passthrough parameter, and rejects unknown input rather than ignoring it. The test asserts the **entire argv equals a known list** for a fixed input, that varying each allowed parameter changes only its own slot, and that no input shape (extra keys, a flag-shaped `agent`, a `--`-prefixed `model`) adds an element. The conformance script's `extraArgs` and `--allowedTools` are probe tooling and are not imported by the adapter. `--settings` carries only the bridge's own value.
7. **Caps.** At most 8 live daemon-spawned sessions regardless of policy; at most 20 pending approvals per cell (older ones expire first, answered deny); at most 2 KB per `message`; SSE keeps its 5 s back-pressure destroy. A cell that floods permission requests or output past the caps has its excess dropped and, past a hard limit, its child stopped.
8. **Cell output is untrusted.** Stdout lines (and transcript lines, if the tailer is on) are model and web-page text. The reader parses each line in try/catch and skips a bad one; caps a line at 1 MB and bounds its buffer when no newline arrives (drop and resync at the next newline); and treats every parsed string as text (never a path, a command or markup). A `control_request` whose shape does not parse is answered deny. If the transcript tailer is enabled it builds the path only from a sessionId matching the UUID pattern and checks with `realpath` that the result, and every sibling subagent file, stays under `~/.claude/projects`. Tests feed it malformed, oversize and path-traversal input.
9. **The registry is untrusted, and the bridge signals only its own children.** `.scratch/_run/sessions.jsonl` is writable by any cell. Replay validates every field (`cellId` against its pattern, `sessionId` as a UUID, `ref` against the dispatch regex, timestamps parseable) and drops what fails. The bridge sends signals only to `ChildProcess` objects it spawned in this run; no pid is ever read from a file, a request or the snapshot, so there is nothing to forge and no process-verification step is needed. The audit lines are tamper-evident only against the UI, not against a cell: a cell can append or edit them.
10. **A spawned cell can edit its own permission surface (partial measure, known gap).** The cell's worktree has its own `.claude/settings.json`, and an unattended cell can add `allow` rules there. The adapter passes the bridge's `deny` rule on `Write` and `Edit` of `.claude/**` as **inline JSON** in `--settings '{"permissions":{"deny":[...]}}'`, not a file *(round 2, F5: no file means no predictable path, no race and nothing a cell can edit; deny rules are not secrets, so argv is fine; if a file ever becomes unavoidable it is created under `mkdtemp` (0700) with the `wx` flag and the bridge never writes `~/.claude.json` or any Claude configuration)*. Whether `--settings` merges and a `deny` outranks a worktree `allow` is spike S6, **rerun as S6b in a real worktree under the repo** (round 2, F8; the first S6 ran in an untrusted temp directory and was unresolved, not failed: the CLI said it ignored the project's `permissions.allow` there because the workspace was not trusted, which says nothing about merge or precedence). *(Amendment 10, loop spec decision 2:)* The same inline value also denies `Bash(git push:*)` and `Bash(gh pr create:*)` for every bridge-run agent, because the project settings auto-allow `git push -u origin feature/*` and `gh pr create` and a deny rule wins over an allow. It is the same kind of partial measure: the rule matches the command as the CLI reads it, so it stops the plain case, not a determined rewrite, and the user still does every push and merge.
    - **Effective permissions are wider than the repo's allowlist** *(round 2, F5)*. S1's `system/init` showed the child loading the owner's user-scope MCP servers (blender, claude.ai connectors), plugins and user settings through `HOME`; user-level `allow` rules and hooks would apply to an unattended cell. The adapter therefore passes `--setting-sources project,local` and `--strict-mcp-config` with no `--mcp-config` (a role that needs an MCP server is a later amendment). S6b checks in `init` that `mcp_servers` and `plugins` carry no user-scope entries and that a user-level allow rule does not apply. `HOME` stays in the environment allowlist because login needs it, so a source that cannot be switched off this way (managed policy, a user hook) is a recorded residual, not a silent one.
    - **Trust is a user action, never bridge code** *(round 2, F8)*. If S6b shows that `.claude/worktrees/*` does not inherit the main checkout's trust (the project's `permissions.allow` is ignored there), the user accepts the trust dialog once in the repo, and that fact is recorded here in an ADR amendment. The bridge never writes trust into `~/.claude.json` (any cell can write that file). The untrusted case fails safe (more approvals, not fewer), so it is a usability cost, not a hole. Until S6b passes, no 106 test asserts deny-over-allow.
    - The fixtures to be committed under `apps/bridge/cells/fixtures/` need a **scrub step** before commit: init holds `cwd`, `memory_paths`, plugin paths (the owner's home path and username), `session_id`, `messaging_socket_path`, and plugin and MCP lists. Keep only the lines and keys the parser needs.
    - The bridge's own files: `.scratch/_run/` is created `0700`, `sessions.jsonl` `0600`, and any temp file the bridge writes goes under `mkdtemp`. These are hygiene, not a defence against a cell on the same account (decision 6, scope sentence). **This does not stop a Bash command from writing the file**, so it is a speed bump, not a wall; a real wall needs an OS sandbox, which is out of scope here (deferred, M6). One detection step stays in scope: slice 1 adds `.claude/**` to the `risk-check` patterns (`scripts/risk-check.mjs` has no `.claude` pattern today) so any such diff dispatches `security`. The posture otherwise matches interactive cells today, except these run unattended.
    - **The agent's own ticket** *(amendment 13, user decision 2026-10-10)*. The board is in the main checkout, outside every agent worktree. In the first live task started from the den (scout, Haiku, CLI 2.1.293) the agent's read of its ticket file raised a permission request, so it waited on the user before it could read its task or claim. The host now passes the runtime the ticket's path, built from the bridge's own root and the validated ref, and the adapter adds one rule to the inline value: `"allow": ["Read(//<absolute path>)"]`. The adapter accepts only a plain absolute path ending `.scratch/<feature>/issues/<name>.md`, with no `.` or `..` segment and no character outside letters, digits, `.`, `_`, `-`, `@`, `+` and `/`, so the rule cannot become a glob or a second rule; a path it cannot write that way is left out and that agent's ticket read stays a request. No client string is involved, and deny still wins over allow. The live check (`npm run smoke:live`, fixtures `live-ticket*.jsonl`) shows the ticket read raising no request and a read of the file next to it still raising one. A symlinked repository path is untested and may leave the read a request.

### 7. The thinnest first slice, and what follows

"Drive agent work from the UI" is reachable on day one with **slice 1 = dispatch + watch + approve + kill**, all over the one headless channel. Because dispatch starts a real `claude` child, "approve" here means both the dispatch click (a token-authenticated `POST /cells`) and the permission inbox.

- **How the bridge is started (open question for the user).** The bridge must run in a process that can reach the owner's `claude` login and is not inside a cell's sandbox (the probe's sandboxed child was "Not logged in"). The user cannot assume a terminal; options to settle, not decided here: the desktop app's own terminal, a double-click or login-item launcher script, or `npm run ui` in any shell. **The user starts the bridge; an agent's tool call never does** (round 2, F2: a launch URL printed into a cell's transcript is readable by any cell until it is spent or expires). Whatever is chosen must show the launch URL somewhere the user can see it and a cell cannot read, and must give the user a way to get a fresh launch code after a closed tab without restarting the bridge (a page reload does not need one: it keeps the session; a bridge restart prints a new code at start) (for example the user pressing Enter in the bridge's console). This ADR assumes no terminal.
- **Reload keeps the session (organism-infra/139, user decision 2026-10-05).** The UI keeps the session token in `sessionStorage`: per tab, gone when the tab closes, and never sent by the browser on its own, so there is no ambient credential for a cross-site page to ride. Not a cookie, and not `localStorage` (it outlives the tab and is shared across tabs). The launch code is never stored; the `#code` fragment is removed from the address bar whether redemption succeeds or fails. A `401` from the bridge clears the stored token, and the UI then shows the one-line "no session" copy until a new launch code is redeemed. A bridge restart drops every token, so the next reload shows that line and the user opens the new launch URL. This replaces the "in memory" wording in decision 6 item 2 for the UI side. **Residual, accepted (security M1):** browsers can persist `sessionStorage` to the profile directory for session restore, so a copy of the token may outlive the tab on disk, readable by any process on the same account (the same class of exposure decision 6 item 2 avoids for a token file). Tokens have no expiry and live until the bridge stops; a bridge restart makes any stale copy dead. Token expiry is filed as organism-infra/152.
- **Spikes first, each a go or no-go before building** (run with the owner's login, via `conformance.mjs`): **S1** a child spawned by a Node process with the allowlisted environment starts logged in, accepts `--session-id <uuid>` and `--agent <cell>` under `-p`, accepts a first stdin user message, emits `system/init` and exits on stdin EOF; the canary variable does not reach it. **S2** the stdout stream delivers a tool event in under one second, and shows whether subagent activity appears (decides the transcript tailer). **S3** `--permission-prompt-tool stdio` emits a `control_request` with the full tool input for a tool outside the allowlist, and a `control_response` allow and deny is honoured; capture the real shapes as fixtures. **S4** SIGTERM ends a running child, keeps the transcript, and `--resume <sessionId>` reopens it. **S5** billing: a five-hour usage reading before and after one trivial headless run, plus the account's usage page (decision 2); the user confirms the result. **S6** `--settings` merge and `deny` precedence over a worktree `allow` (6.10); its first run was **unresolved, not failed** (untrusted temp workspace), so S6b replaces it. If S1 fails because the owner's login does not reach a child of the bridge, slice 1 is blocked and goes back to the user (the fallback is a different process owner, not a different design here). If S3 fails, slice 1 ships without the inbox (decision 3, Permissions) and approval moves to slice 2.
- **Spike round 2 (S8, S4b, S6b, S3b)** *(security round 2)*. All run by the user with their own login through `conformance.mjs`, which ticket A extends (ids are case-insensitive on the command line: `--spike S8,S4b,S6b,S3b`). Each prints go, no-go or unconfirmed with evidence, saves fixtures with the owner's home path and username scrubbed, and spends about 8 to 12 turns on the cheap model in total. Nobody but the user runs them: a cell's sandbox has no login.
  - **S8, the child's messaging socket (F1; gates the adapter).** Spawn a child as S1 does, with `--permission-prompt-tool stdio` and a long allowed tool call available. (1) Read `messaging_socket_path` and `capabilities` from `system/init`; if absent or null, record it and stop (outcome a). (2) `stat` the socket and its directory: file type, mode, owner uid against this process's uid, and whether `others` have read or write (an open `/tmp/cc-socks` would also expose it to other OS users). (3) From a **separate plain `node:net` client** in the runner (a stand-in for any process on the account, using none of the child's pipes), connect and record whether it connects, any unsolicited bytes in 2 s (an event leak is a finding on its own), and any greeting. (4) Send probes as newline-delimited JSON and watch the child's **stdout** for an effect after each: (i) a user message carrying a random nonce, effect if an assistant line echoes the nonce; (ii) an interrupt (both `{type:"control_request",request:{subtype:"interrupt"}}` and `{type:"interrupt"}`) while a `sleep 15` tool call runs, effect if the tool result arrives early or errors; (iii) while a `can_use_tool` request for a write outside the allowlist is pending and **unanswered on stdin**, a `control_response` allow naming its real `request_id` over the socket, effect if the file appears. The runner then denies on stdin and ends the child. (5) If a socket existed, try disabling it: candidate flags from lines of `claude --help` matching `socket|messaging|inbound`, plus any `--s8-disable-flag <flag>` and `--s8-disable-env NAME=VALUE` the user supplies from their own reading (repeatable); a candidate counts only if `messaging_socket_path` is gone or the socket file absent **and** the child still logs in and answers. **Verdict:** go for outcomes (a) and (b) of 6.3, `residual` for (c) (messages or interrupts accepted, `control_response` not), no-go for (d), and `unconfirmed` (treated as no-go for the inbox) when the socket accepts a connection but the shapes tried show nothing either way. The evidence lists every shape tried, so `security` can judge how much silence proves.
  - **S4b, kill and exit during a tool call (F6).** Each run starts a child with `Bash(sleep 61)` allowed, asks it to run `sleep 61`, waits for the `tool_use` line plus 1.5 s, and records the child's pid and process group and the pids of every process whose command is `sleep 61` (`ps -axo pid,pgid,ppid,command`). (1) **EOF mid-call:** close stdin only, poll 15 s: did the child exit, and did the `sleep` survive? (2) **SIGTERM to the child alone:** exit time and `sleep` survival at +2 s and +10 s. (3) **SIGKILL to the child alone:** `sleep` survival. (4) If any `sleep` survived in (1) to (3), repeat (2) and (3) with the child spawned `detached: true` and the signal sent to the process group (`process.kill(-pid, ...)`). The runner always `SIGKILL`s leftover `sleep` pids it recorded at the end. **Verdict:** go (`decision: plain`) if the child exits on EOF mid-call and no `sleep` survives any run; go with `decision: group-kill` if survivors appear and the group signal clears them (decision 2 then requires the process-group spawn); no-go if survivors outlive the group signal, or if the child does not exit on EOF mid-call (the "bridge exit ends its cells" claim is then unproved and the shutdown handler is the only protection, which goes to the user).
  - **S6b, `--settings` precedence and setting sources in a real worktree (F5, F8).** `--repo <path>` (default: the repository containing the script) names a repo the owner has already trusted by running `claude` there interactively once; the script says so. It runs `git worktree add --detach <repo>/.claude/worktrees/s6b-<random> HEAD` and always removes it (`git worktree remove --force`) afterwards. In the worktree it writes `.claude/settings.local.json` with `permissions.allow` for `Write(allowed.txt)` and `Write(.claude/**)` and a probe role file, then spawns with the production-shaped arguments: `--setting-sources project,local`, `--strict-mcp-config`, and the deny rule as **inline JSON** in `--settings`. The prompt writes `allowed.txt` and then `.claude/probe.txt`. **Checks:** (1) `allowed.txt` exists (the project allow applied, so the worktree is trusted) and `.claude/probe.txt` does not (deny outranks allow, and inline `--settings` JSON merged rather than replaced); (2) stderr does not say the workspace is untrusted (if it does: verdict `unconfirmed` with the evidence that a worktree under `.claude/worktrees` does not inherit trust, which is the user's action to take and record, 6.10); (3) `init.mcp_servers` has no entry whose source is `user` or `claudeai`, and `init.plugins` has no user-scope plugin. **Verdict:** go needs (1) and (3); a failed (3) is no-go and the evidence names what leaked (a user-level allow rule or hook cannot be probed without editing the owner's settings, so it stays a stated residual).
