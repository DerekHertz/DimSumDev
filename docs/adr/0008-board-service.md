# The `board` CLI is the single writer of the board; no daemon IPC until parallel cells (amends ADR 0003)

> Terms: written before ADR 0028, which renamed the vocabulary (cell → agent, cell type → role, genome → role definition, station → team, organism → the org, apoptosis → hand off and exit).

**Context.** ADR 0003 put the board on local markdown with lock-file claims, read and written by whichever cell holds the file tools. Two pains fall out of that as the organism grows: a cell running in a worktree can't write the main checkout's board with its file tools at all (the desktop app's worktree guard blocks it — cells currently improvise shell writes as a sanctioned exception), and lock-file claims plus multi-step edits (set `Status:`, append `## Comments`, delete `.lock`) aren't atomic as a unit, so two cells can interleave and corrupt a ticket. This ADR's first draft solved that with a daemon-owned board service reached over a named pipe / Unix domain socket. Security review (`.scratch/organism-infra/handoffs/01-security.md`) found the transport itself carried real cost: Node gives Windows named pipes a default DACL that lets any local process read them, pipe names can be squatted before the daemon starts, and a shared subscribe stream needs backpressure handling — all fixable, but not for free. Under ADR 0002's `max_concurrent_cells: 1`, the board never has more than one writing cell at a time, so that cost buys nothing yet: both pains above are fully solved by a CLI with per-mutation file locking, no daemon or IPC required. Revised per the user-approved joint architect/orchestrator recommendation (2026-09-27) to descope to CLI-only until parallel cells make a second concurrent writer real.

**Decision.**

1. **Seam.** One module, the board service, exposes six operations — claim, release, status, comment, list, subscribe — implementing markdown parsing/editing, per-mutation locking, atomic writes and event sequencing. Today it has exactly one adapter: the `board` CLI calls it in-process. The module's interface doesn't change if a daemon-IPC wrapper is added later (decision 5); that remains the seam ticket 02 builds against.

2. **Locking: two separate locks, not one.** A **write lock** guards the full read-modify-write of every mutating op (claim, release, status, comment) — held for milliseconds, around one operation. Its file contains `{pid, host, createdAt}`. It is reclaimable only when all three hold: the lock's `host` matches the reclaiming process's host, `process.kill(pid, 0)` (or the OS-equivalent liveness check) reports the `pid` is not alive, and its `createdAt` age exceeds a few seconds (a floor against reclaiming a live-but-just-started lock before its liveness check would even be meaningful). A lock from a different `host` is never auto-reclaimed. Reclaim is race-free: rename the stale lock file to a unique tombstone name first (only one racing reclaimer's rename can succeed — the others fail and back off), then retry the `O_EXCL` create; a create failure at that point means someone else already holds a fresh lock, not a fatal error. This closes the fallback-atomicity gap security flagged in the first draft (release/comment weren't locked at all) without the round-2 finding (time and liveness conflated, no PID to check against).

   The **claim lock** — the `.lock` file recording ticket ownership per `docs/agents/issue-tracker.md` — is a different lock with a different lifetime: held for hours across a whole ticket, and never auto-expires. Only `board release` (which deletes it as part of its atomic status-change call) or the user clears it by hand. Ticket 02 must implement these as two independent mechanisms, not one generalized "lock file with a timeout": the write lock's reclaim logic (PID+host+age, tombstone-rename, retry) never applies to the claim lock, and the claim lock's absence of expiry never applies to the write lock. Markdown edits are written via temp-file-plus-rename regardless, so a reader never observes a half-written file even mid-mutation.

3. **CLI command set**, one per board-service operation: `board claim <feature>/<NN-slug> <cell-type>`; `board release <feature>/<NN-slug> --status <status> [--reason "..."]` (one atomic call, replacing "edit Status:, delete lock"); `board status <feature>/<NN-slug>`; `board comment <feature>/<NN-slug> "<text>"`; `board list [--feature X] [--status Y]`; `board subscribe [--feature X] [--since <seq>]`, which tails `events.jsonl` directly (no daemon connection to hold open). Reading a ticket's body stays a plain file read; only mutations go through `board`.

4. **`events.jsonl` schema**, unchanged: one JSON object per line, appended by every mutating call: `{seq, ts, feature, ticket, cell, op, from_status?, to_status?, text?}`. `seq` is a monotonic counter continued from the log's last line; `cell` identifies cell-type plus session/worktree id; `op` is `claim`, `release` or `comment`. The log is an append-only side feed for subscribers; markdown remains the sole source of truth for ticket content.

5. **Daemon IPC is deferred, not designed out.** No board IPC ships until parallel cells (`max_concurrent_cells > 1`) make a second concurrent writer real; ticket 03 (daemon board service) is on hold until then. The first draft's IPC-specific findings stop applying because there is no IPC surface to carry them: no named pipe exists, so its default-DACL read exposure is moot; nothing listens on a well-known name, so there's nothing to squat; there is no Unix socket file or its containing directory to lock down; and `subscribe` tails the file directly, so there's no shared daemon-side connection buffer to apply backpressure to — each subscriber manages its own file-read pace. When parallel cells do ship, the module boundary in decision 1 makes a daemon wrapper additive: it gets its own ADR, which must design the pipe/socket security properly (an explicit DACL, first-instance pipe creation, a locked-down socket directory) rather than assume OS defaults are safe.

6. **Ticket 02 requirements**, folded in from security review: validate `feature` and ticket-id strings against a strict allowlist (`^[a-z0-9-]+$` / `^\d{2}-[a-z0-9-]+$`) before any path join, then resolve and verify the joined path stays under the board root before any read/write, rejecting `..`, absolute paths, and symlink escapes; cap accepted comment/arg length before parsing; the locking in decision 2 applies to every mutating operation, not just claim.

7. **Auth and exposure.** The `board` CLI is a local process invoked directly by a cell or the user, with the same filesystem permissions any of their other tools already have — it introduces no new privilege boundary or network-reachable surface. Whoever can run a shell command in the repo could already edit the markdown and lock files directly (ADR 0003's status quo); `board` only serializes and validates those writes.

8. **Out of scope here: steering live cells.** The daemon↔UI↔cell channel — the UI sending commands to a running cell (approve/deny, pair, kill) and live cell state reaching the UI faster than a board event — is a different seam with a different client (a browser, which can't open a named pipe or Unix socket at all). That transport is ticket `organism-infra/11`'s question, not this ADR's.

9. **Claim ergonomics and cell identity (ticket `organism-infra/24`).** Three commands join the set in decision 3. `board reclaim <ref> <cell> --reason "..." [--mode m]` takes over an existing claim lock in one call; `<cell>` is never `orchestrator`, and the reason is stored in the event (`op: reclaim`, with `previous_cell`). `board comment <ref> [--as <cell>] "<text>"` names the author: with a claim lock, `--as` must equal the lock's cell; without one, `--as` is the author; with neither, the comment is rejected. `board release <ref> --keep-status` frees the lock and leaves the ticket unchanged, and excludes `--status`. Only a claim held by `orchestrator` may release at `resolved`; `--force` does not bypass that. Every cell name on `claim`, `reclaim` and `--as` must be one of the nine known cells, so it cannot carry markup or line breaks. **Limit:** cell identity is self-declared, not authenticated. Validation guarantees a name is a real cell, not that the caller is that cell; `claim <ref> orchestrator` on an unlocked ticket stays open by design, consistent with decision 7.

10. **Review claims keep `in-review` (ticket `organism-infra/28`).** A claim by `security`, or by `qa` with `--mode verify`, on an `in-review` ticket leaves the status at `in-review` while the lock is held; every other claim sets `claimed`. The claim event's `to_status` records the actual status. Consequence: an `in-review` ticket looks the same whether or not a review is in flight, so the orchestrator checks for the `.lock` file before dispatching a reviewer. A dead review lock is recovered with `reclaim` or `release --keep-status`.

11. **Release gate binds to the releasing cell (ticket `organism-infra/35`).** Every `op: release` event carries `force: true|false`, so a bypassed gate is visible in the log. The handoff gate on `release --status in-review|resolved` now accepts a handoff only if its State block `cell` equals the claim's cell, its `mode` equals the claim's mode when the claim has one, and its file mtime is at least the claim lock's mtime. Before this, any `<NN>-*.md` naming the ticket satisfied the gate, so a developer release passed on qa's earlier handoff (ticket 34). **Limit:** `cell`/`mode` in the State block are self-declared, like the claim itself (decision 9), and mtime can be set by anyone; the gate catches stale or wrong-hop handoffs, not forgery. A gated release (`--status in-review|resolved`, `--keep-status`) with no claim lock is refused, since there is no cell, mode or age to bind to (ticket `organism-infra/45`); only `--force --reason` bypasses it. The risk-check secret patterns also cover GitHub (`ghp_`), `sk-` (word-boundary) and Slack (`xox[abp]-`) tokens.

12. **Scripted usage rows (ticket `organism-infra/48`).** The `.scratch/usage.jsonl` rows for outcomes are written by scripts, not by hand. `board comment <ref> --verdict pass|bounce "<text>"` records `verdict` on the `op: comment` event in `events.jsonl`; any other value is refused and nothing is written. `board release <ref> --status resolved [--pr N]` appends one `{kind:"resolved", ts, ticket, pr, bounces}` row after the release commits, where `bounces` is the count of that ticket's comment events with `verdict: "bounce"` (free text saying "bounce" counts nothing). `--pr` must be a positive integer and is required when the ticket's `**Type:**` is `feature` or `bug`; a missing or bad value fails before any write and leaves the claim. Other types write `pr: null`. `node scripts/log-cell.mjs --ticket <ref> --cell <type> [--mode m] --tokens N --ms N --outcome "..."` appends one validated `{kind:"cell", ...}` row (ticket must exist, cell must be known, tokens and ms non-negative integers, outcome non-empty). ADR 0010's `kind:"jev"` rows are still written by `jev.mjs`.
13. **Verdict roles, specify claims and usage-row hardening (ticket `organism-infra/49`).** `board comment --verdict` is accepted only from the qa, security and orchestrator cells (lock cell or `--as`); any other author is refused with nothing written, so a developer cannot forge a verdict. A qa claim in mode `specify` on an `in-review` ticket leaves the status `in-review`, like verify and security claims (the ticket 28 review-claim rule extended); other statuses still set `claimed`. If the resolved-row append fails after `board release --status resolved` has committed, release exits non-zero naming `usage.jsonl` and the redo command; `node scripts/log-resolved.mjs --ticket <ref> [--pr N]` appends the same row, and refuses a ticket that is not resolved or one that already has a resolved row. Appends to `usage.jsonl` (board and `log-cell.mjs`) refuse a symlinked file (`O_NOFOLLOW`); `log-cell` caps `--outcome` at 500 and `--mode` at 32 characters. `--pr` on any release that is not `--status resolved` is refused before any write.
14. **Verdict claim lock and failure rows (ticket `organism-infra/50`).** `board comment --verdict` requires a claim lock on the ticket, for every author including the orchestrator, with or without `--as`; the author is the lock's cell and `--as` must match it. A qa lock permits a verdict only in mode `verify` (a `specify` lock is refused); security and orchestrator locks need no mode. A refusal names "verdict" and "lock" and writes nothing. Comments without `--verdict` keep the old rules (`--as` with no lock still works). `log-cell.mjs` gains `--failures "<tool>:<what>;<tool>:<what>"`: items split on `;`, each on its first `:`, and one `{kind:"incident", ts, ticket, cell, tool, what, cost:null, fix:null, rule_change:null, source:"cell-report"}` row is appended after the cell row, in order. `tool` is one of bash-guard, board-claim, board-release, board-comment, board-handoff, handoff-state, git, npm, write, ci, other; `what` is non-empty and at most 300 characters. Any bad item refuses the whole call with nothing written, the cell row included. `log-cell` also refuses a symlinked `.scratch` directory, as `log-resolved` does. `log-resolved` runs its duplicate check and append under the board write lock, so concurrent runs write one row.

**Considered options.**
- *Daemon-owned board service reached over a named pipe / Unix domain socket.* This ADR's first draft. Deferred per decision 5: the transport-specific attack surface it opens isn't justified while the board has only ever one writer.
- *Loopback HTTP + bearer token.* Rejected outright regardless of daemon timing: an open TCP port plus a token file protected the same way a socket path already would be, for no added capability.
- *External broker (Redis, RabbitMQ) for the event queue.* Rejected: out of scope per the ticket, and unjustified — a single writer with an append-only file is durable across restarts already; a broker adds an operational dependency to what ADR 0002/0003 keep deliberately offline and simple.

**Consequences.**
- Ticket 02 (board CLI) is the only implementation ticket this ADR unblocks now: the CLI links the board-service module directly, no IPC branch needed.
- Ticket 03 (daemon board service) stays blocked/on-hold until parallel cells ship; when it's picked up, it needs its own ADR for the pipe/socket security decisions 5 defers, not a reopening of this one.
- Ticket `organism-infra/11` (daemon↔UI↔cell steering and live state) is a separate seam, undecided here.
- `.lock` files stay the on-disk claim marker, format unchanged; this ADR concentrates who writes the board and how each mutation is locked, not the claim mechanism itself.
- CONTEXT.md's **Board service** entry is reworded in this same commit to "the module behind the `board` CLI; the single writer of the board," dropping "it lives in the daemon" now that the daemon wrapper is deferred.
