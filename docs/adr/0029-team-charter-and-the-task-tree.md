# A team charter, four new roles, and a tree per task instead of a fixed relay

**Status:** proposed. The user accepts it by merging its PR. The decisions were settled with the user in a grilling session on 2026-10-19 (team-and-den-ux/02); the full record, D1 to D28, is `.scratch/team-and-den-ux/relay-decisions.md`, and each decision below cites its number. It amends ADR 0002 (concurrency), ADR 0022 decisions 3, 5 and 6, ADR 0024 (who the release steps belong to, two reviews, the tree's record) and ADR 0027 decisions 3 and 11. "Relay size" in `team-protocol` (den-mvp/71) gives way to the planner's floor (decision 3) when team-and-den-ux/17 builds it. The per-role contracts live in `docs/agents/team-charter.md`.

**Context.** Today's relay is fixed by risk: a risk-path ticket runs qa `specify`, developer, qa `verify` and, on a `risk-check` hit, security; any other ticket skips `specify`. The developer reviews its own work, and the orchestrator plans, dispatches, opens the pull request and merges. The team spec (`.scratch/team-and-den-ux/spec.md`, decisions 3 to 5) adds four roles (code reviewer, release manager, SRE, technical writer) and asked for the relay to be redesigned around them rather than bolted on. A second executive, Jiao on Codex, is coming (codex-residents), and so are task trees (codex-residents/07, 09, 11). The user's principle: approval follows the permissions of the task. Where the guardrails, the sandbox and the state are well defined, work does not need the user's approval.

## Decision

1. **A tree per task, not a fixed relay (D1, D18, D23).** Each owned task is a tree of at most 21 nodes: the owner at the root, up to four role managers under it, up to four runners under each. That is a maximum, not a target, and two tasks are two trees. The owner breaks the task down and passes parts to the managers it needs. Each manager breaks its part into scoped subtasks for its runners, reviews what they return, and passes it up. The owner reviews the outcome against the ticket and presents it to the user. Expensive models stay at the top with short contexts: they define work, quiz and review.
2. **Review in four layers (D23, D5).** (1) Each manager reviews its own runners' output. (2) Independent sibling managers review the engineer's candidate commit: the code reviewer reads the diff (standards, design, simplicity, spec fit), qa checks behaviour, and security joins on a hit. Nobody reviews their own subtree. (3) The owner reviews the outcome against the ticket. (4) The user sees the outcome and approves only at the points in decision 8.
3. **The planner's rules set a floor; the owner adds (D21, D8, D27).** A pure planner reads a ticket's type and changed paths and names the roles it must have: the code reviewer on every code ticket and on changes to agent instructions (CLAUDE.md, role definitions, skills) and ADRs; qa on code; security on a `risk-check` hit or a user-merge-list path; the technical writer on a docs ticket or a change to user-facing behaviour or CONTEXT terms; the user's verdict on UI and asset tickets. The owner may add any role but never drop a required one, and the bridge refuses a hand-up that skips a required review. Small tasks call only the roles they need. Plain docs get the writer and the owner's review; research and design tickets get the owner's review and the user's verdict where the ticket asks for one. No qa on non-code.
4. **Two executives, one owner per task (D2, D11, D13, D14, D15, D19).** Bao (Claude) and Jiao (Codex) are peers. Every ticket, project or task has exactly one owner, agreed when it is filed or approved and recorded as `owner: bao|jiao` (the user may override); a change of owner is an explicit, recorded handover. A tree may mix runtimes: the owner picks each node's runtime from a rule (the role's default, for example the reviewer on the other runtime from the engineer's) and what is free under usage limits, and records the pick. An unavailable runtime means the node waits or stops for the user, never a silent switch. When the executives disagree, they write a decision brief (both positions, two or three options, a recommendation from each) that reaches the user under Needs you, and nothing moves on that point until the user chooses. The orchestrator's planning, ticketing, work order and retros fold into the executives; no orchestrator role remains (decision 10).
5. **The roles (D3, D4, D5, D6, D7, D8, D9, D20, D22, D25).** The charter (`docs/agents/team-charter.md`) gives each its inputs, outputs, authority and hand-offs.
   - **Engineer** (the developer role) writes the failing tests first, then the change, and lists each criterion's test. It no longer reviews its own work.
   - **Code reviewer** (new, Tea & Pantry) reviews every code ticket's candidate commit independently and returns `pass` or `bounce` tied to that commit.
   - **qa** reviews behaviour at the same commit, in parallel with the reviewer. Its `specify` mode is retired: the reviewer and qa check that each criterion's test fails without the change.
   - **Security** keeps its trigger: `risk-check` runs on every candidate, and a hit or a user-merge-list path adds security.
   - **Release manager** (new, the Pass): push, pull request, waiting for checks and merge-on-green stay deterministic bridge steps (ADR 0024 decision 4), recorded under the release manager's name; the bridge still makes the git calls and holds the login. An agent runs only for judgment: diagnosing a red, conflicted or unmergeable PR and proposing a fix, cutting a tag and release notes when a spec's tickets all resolve, writing the den update proposal after a bridge change merges, and a weekly digest. It never merges a user-merge-list change and never pushes CI config.
   - **SRE** (new, Tea & Pantry) observes and proposes: health, logs, resource use, delivery and update records in; health reports, tickets and proposed fixes out. Restarts, rollbacks and limit changes are proposals the user approves. It runs on a schedule and on an `environment` stop.
   - **Technical writer** (new, Front of House) updates docs on the ticket's branch after the engineer and before review, runs a scheduled docs-drift sweep that files tickets, and drafts public posts on demand (herald folds in; the user publishes).
   - **Runner** absorbs scout as a read-only mode. The manager picks each runner's model and runtime per subtask. Runners start no agent and hand back a result and evidence.
   - **Product, architect and designer** are managers the owner adds when needed. Their sessions with the user are never auto-advanced: the tree waits at that node while other branches carry on (keeps ADR 0022 decision 7).
6. **Bounces (D12).** The engineer gets one fix round with both reviews' findings, after both have reported. A new commit re-runs both reviews. Two fix rounds, from either reviewer, pause the ticket as failed twice.
7. **The bridge keeps the record (D26).** Agents run no board commands and push nothing. A runner's result goes to its manager. A manager's last message ends with a fixed result block (the engineer: the candidate commit) or `VERDICT: pass|bounce` (reviewers), tied to a commit. The bridge writes claims, handoffs and the tree's record, and refuses a hand-up whose evidence names another commit. Every input and output passes through that record, so no role reads another's private conversation. This settles ADR 0022 decision 5's open item: hop agents do not write the board.
8. **What stays the user's (D16, D17).** Approving a ticket that changes the bridge, guardrails, scripts or CI (the user-merge list); visual verdicts on UI and asset changes, before the merge; merging a user-merge-list change (the release manager prepares it); adding a dependency, a purchase, a new account, API key or outbound service; accepting an ADR, and changes to CLAUDE.md, role definitions and skills; SRE's restart, rollback and limit proposals and the per-layer caps; the release manager's den update proposals; a decision brief, a scope question no spec answers, a twice-failed ticket, an environment stop, and usage at 90% or more. Agents may file and start tickets inside approved work (follow-ups, bugs found, docs drift, SRE findings) when the ticket touches nothing on the user-merge list; a new direction or project still comes to the user, and each self-filed ticket shows who filed it and why.
9. **Concurrency: per-layer caps, measured (D24).** `max_concurrent_agents: 2` gives way to a cap per layer, gated by machine resources (`limits.json`) and the live usage reading (no new spawn at 90%). The starting point to measure is two executives, four live managers and eight live runners. There are no token, cost or time caps. The architect sets the starting numbers from a measured trial and the user approves them, because they sit on the wall.
10. **Direct work stays (D28).** The user may give any role a focused job from the den, outside a tree, still behind the wall and the resource limits. Push, PR and merge still go through the release manager's checks.

## Consequences

- The developer's self-review goes away; an independent reviewer and qa read every code ticket, so a code ticket costs one more review run. Docs-only and research tickets stop paying for qa.
- Push, PR and merge have a named owner, so a red or conflicted PR can get a diagnosis instead of only a pause (from team-and-den-ux/20).
- The relay stops being one shape. The floor keeps independent review compulsory where it matters; the owner's choices above it are recorded, so a retro can see what a task paid for.
- Until the follow-ups land, two vocabularies coexist: the orchestrator, herald and scout still run, and their role definitions name the role that replaces them.
