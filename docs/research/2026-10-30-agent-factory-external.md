# Agent factories: external evidence (2026-10-30)

Question: how do others build and run multi-agent software "factories" on Claude Code and comparable tools, and what should the den keep, drop or copy?

Method: Claude Code docs read directly on 2026-10-30 (code.claude.com). Anthropic engineering posts: the multi-agent research post was read directly; the harness and context-engineering posts were seen only through search results (marked). Practitioner and tool claims come from web searches, mostly secondary write-ups; each is marked **[verified]** (read at the source this session), **[secondary]** (search summary or third-party write-up) or **[unverified]** (canonical URL given from prior knowledge, not re-read today). The context budget ran out before every row could be checked at its source, so treat [secondary] and [unverified] rows as leads, not facts.

## 1. Platform capabilities, and what they would replace in the den

All rows in this table are **[verified]** against code.claude.com on 2026-10-30.

| Capability | Fact (cited) | What it could replace in the den |
| :- | :- | :- |

Anthropic engineering posts:
- Multi-agent research system (2025-06-13) **[verified]**: Opus 4 lead + Sonnet 4 subagents beat single Opus 4 by 90.2% on an internal research eval; agents use ~4x chat tokens, multi-agent ~15x; token usage explains 80% of BrowseComp variance; multi-agent fits poorly where agents need shared context or have many dependencies, and "most coding tasks involve fewer truly parallelizable tasks than research." https://www.anthropic.com/engineering/multi-agent-research-system
- Effective harnesses for long-running agents (2025-11-26) **[secondary]**: an initializer agent writes a feature list (JSON, because models rewrite markdown) and a `claude-progress.txt`; each coding session reads progress + git log, works one feature, and leaves a mergeable state. https://anthropic.com/engineering/effective-harnesses-for-long-running-agents
- Effective context engineering (2025-09-29) **[secondary]**: context is a finite attention budget; sub-agents return condensed summaries; compaction, structured notes and sub-agents are the long-horizon tools. https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## 3. Practitioner consensus and disagreements

Consensus (where several sources agree):
- **Parallelism pays for breadth, not for coupled coding.** Anthropic's own data says multi-agent wins on parallelizable research and is a poor fit for coding with shared context (fact, https://www.anthropic.com/engineering/multi-agent-research-system). The Claude Code docs repeat it: teams "use significantly more tokens" and for "sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; start with research and review (fact, https://code.claude.com/docs/en/agent-teams).
- **Isolation by worktree + file partitioning.** Docs make worktrees the default for dispatched sessions and tell teams to give each teammate its own files (fact, https://code.claude.com/docs/en/agent-view.md, https://code.claude.com/docs/en/agent-teams).
- **External state beats memory.** Progress files, git history and a JSON feature list let a fresh context resume (Anthropic, [secondary], https://anthropic.com/engineering/effective-harnesses-for-long-running-agents); Gas Town keeps work in git-backed "Beads" so it survives restarts ([secondary], https://pkg.go.dev/github.com/steveyegge/gastown).
- **Parallel adversarial review is the safest multi-agent use.** Docs' worked examples are a three-lens PR review and competing-hypotheses debugging (fact, https://code.claude.com/docs/en/agent-teams); workflows advertise adversarial cross-checking as the quality pattern (fact, https://code.claude.com/docs/en/workflows.md).
- **Capture lessons back into the system.** Kieran Klaassen's "compound engineering" loop (plan, work, review, compound) writes each lesson into prompts/agents (opinion, Klaassen/Every, [secondary], https://every.to/napkin-math/inside-the-100-agent-software-factory , https://www.mintlify.com/EveryInc/compound-engineering-plugin).

Disagreements:
- **Scale.** Yegge's Gas Town runs a Mayor, worker "polecats", a witness and a "refinery" for merges across 10-30+ agents (opinion/claims, [secondary], https://heise.de/-11178824 , https://pkg.go.dev/github.com/steveyegge/gastown); reviewers report ~$100/hour burn and call it overkill for solo developers ([secondary], https://dev.to/kiwibreaksme/what-i-learned-from-steve-yegges-gas-town-and-a-small-tool-for-solo-developers-2me2). Anthropic's docs default Pro users to `small` (<5 agent) workflows (fact, https://code.claude.com/docs/en/workflows.md).
- **Evidence quality.** No public benchmark compares compound engineering with plain disciplined single-agent use; claims rest on testimony ([secondary], https://developertoolkit.ai/en/method/principles/compound-engineering/).
- **Role-play vs. function.** Not settled by any source found here. Anthropic's role examples are *lenses* (security, performance, tests; UX, architecture, devil's advocate), not an org chart (fact, https://code.claude.com/docs/en/agent-teams). I found no primary evidence that a full engineering-org of roles beats a single agent + good tests on coding throughput.

## 5. Portability patterns

- **Plugin + marketplace** is the documented unit: one repo with `.claude-plugin/marketplace.json`, plugins namespaced (`den:developer`), versions pinned by `version` (fact, https://code.claude.com/docs/en/plugins-reference). Every's compound-engineering ships this way ([secondary], https://www.mintlify.com/EveryInc/compound-engineering-plugin).
- **Same plugin in CI** via `plugin_marketplaces` + `plugins` inputs and a `/plugin:skill` prompt (fact, https://code.claude.com/docs/en/github-actions.md).
- **Per-project values via `userConfig`**, state via `${CLAUDE_PLUGIN_DATA}`, project files via `${CLAUDE_PROJECT_DIR}` (fact, https://code.claude.com/docs/en/plugins-reference).
- **Workflows as plugin components** make an orchestration portable as code, not prose (fact, https://code.claude.com/docs/en/workflows.md).
- **AGENTS.md** for cross-vendor instructions ([unverified], https://agents.md).

## 6. Implications for the den

1. Move relay sequencing into a plugin-shipped dynamic workflow (developer, then `parallel(code-reviewer, qa)`, then risk-check, then security on a hit) with JSON-schema verdicts; each user gate becomes a separate workflow stage, since workflows take no mid-run input. https://code.claude.com/docs/en/workflows.md
2. Use `isolation: worktree` in the developer role instead of bridge-created worktrees. https://code.claude.com/docs/en/sub-agents
3. Do not move role frontmatter `hooks`/`mcpServers`/`permissionMode` into the plugin's agent files: plugin subagents ignore them. Put guards in plugin `hooks/hooks.json` or project settings. https://code.claude.com/docs/en/sub-agents
4. Read `claude agents --json --all` for session state rather than tracking processes, if the den adopts background sessions; it is the documented stable surface. https://code.claude.com/docs/en/agent-view.md
5. Replace the custom usage reading in `usage-watch` with `rate_limits.five_hour.used_percentage` from status line JSON, handling absence. https://code.claude.com/docs/en/statusline.md
6. Set `sandbox.failIfUnavailable: true` and an explicit `network.allowedDomains` as the wall's baseline, and remember the sandbox does not cover Edit/Write or MCP. https://code.claude.com/docs/en/sandboxing.md
7. Keep `max_concurrent_agents: 2` and prefer review/qa parallelism over parallel implementation: Anthropic finds coding has few truly parallel tasks, and multi-agent costs ~15x chat tokens. https://www.anthropic.com/engineering/multi-agent-research-system
8. Watch agent teams but do not build on them yet: experimental, no `-p`/SDK, no resume, no worktree isolation. Their `TaskCompleted` exit-2 gate is the pattern to copy now. https://code.claude.com/docs/en/agent-teams
9. Add `claude plugin eval` cases with a no-plugin baseline for the den plugin, to answer "do roles beat one agent + tests?" with numbers instead of testimony. https://code.claude.com/docs/en/plugin-evals.md , https://developertoolkit.ai/en/method/principles/compound-engineering/
10. Keep the board's state in files + git (progress note, JSON criteria) so a fresh agent can resume; this matches Anthropic's harness and Gas Town's Beads. https://anthropic.com/engineering/effective-harnesses-for-long-running-agents , https://pkg.go.dev/github.com/steveyegge/gastown
11. Treat a merge step as its own role/queue (Gas Town's refinery) only if parallel PRs start conflicting; at two workers the release-manager-on-green flow is enough. https://heise.de/-11178824
12. Put the `pipeline-retro` / `reflect` output back into role files after each run, the "compound" step; this is the cheapest claimed win, though unbenchmarked. https://every.to/napkin-math/inside-the-100-agent-software-factory

## Practitioner evidence (forums and blogs)

Tags: [verified] = page opened 2026-10-30. Forum quotes are single users' opinions, attributed by handle. Reddit (r/ClaudeAI, r/ClaudeCode) refused automated fetches and search returned no Reddit threads, so Reddit is not covered; a web search for it returned only secondary guides, which repeat the docs' 3-7x team token figure.

**Do role-based multi-agent orgs beat one agent + tests + review?** No source shows they do. Several practitioners reject roles as personas and keep subagents for context isolation.
- Huntley's "Ralph" is deliberately one process: it "works autonomously in a single repository as a single process that performs one task per loop"; tests and builds are "back pressure to reject invalid code generation" (opinion, Geoffrey Huntley, [verified] https://ghuntley.com/ralph/). He scopes it to greenfield work, with a senior engineer steering.
- Hashimoto runs one agent at a time: "I'm not [yet?] running multiple agents, and currently don't really want to" (opinion, Mitchell Hashimoto, [verified] https://mitchellh.com/writing/my-ai-adoption-journey).
- HN on Claude Code subagents: "don't make subagents for the different roles, make them to manage context for token heavy tasks" (lucraft); "the primary benefit for subagents is context/focus management" (CharlesW); personas are "more theatre then utilty" (skimojoe) ([verified] https://news.ycombinator.com/item?id=45181577).
- HN on Gas Town v1.0: "most of the complexity of gas town is absolutely not needed and probably detrimental" (sailingparrot); "high token overhead (inter agent communications, agents re reading same code, etc...)" (guybedo); "the same claude running everywhere with the same system prompt" (0x457) ([verified] https://news.ycombinator.com/item?id=47770124). Optimists call multi-agent coordination "obviously what's next" while expecting Gas Town to stay "a proof-of-concept" (theptip, [verified] https://news.ycombinator.com/item?id=46734302).
- The pro case comes from Every: "Roughly 80 percent of compound engineering is in the plan and review parts", and their review step runs "12 subagents that each check it from a different perspective" (opinion, Klaassen/Shipper, [verified] https://every.to/chain-of-thought/compound-engineering-how-every-codes-with-agents). The parallel agents there are review lenses. Nobody describes an org chart of implementers.

**Orchestration overhead, cost, babysitting.**
- Review is the bottleneck: "the natural bottleneck on all of this is how fast I can review the results"; "I can only focus on reviewing and landing one significant change at a time"; "Code that started from your own specification is a lot less effort to review" (Simon Willison, [verified] https://simonwillison.net/2025/Oct/5/parallel-coding-agents/). On HN: "The current bottleneck is validation" (CuriouslyC); parallel branches "a lot of the time end up in merge conflicts" (ramoz) ([verified] https://news.ycombinator.com/item?id=47218318).
- Realistic width is 2-3 agents: "2-3 focused agents (one on backend, one on frontend, one on tests)" and "the spec quality is everything" (evara-ai). Cost bites: "the parallel agents burn though tokens extremely quickly" (ecliptik); "I usually hit weekly quota by around day 3-4" (gck1) (same thread, [verified]).
- Coordinator models re-pay context: "you are paying for the same tokens repeatedly" (storystarling, [verified] https://news.ycombinator.com/item?id=46734302). Gas Town "scorches tokens but it was able to get larger prototypes done" (jcims, [verified] https://news.ycombinator.com/item?id=47770124). Subagent chaining "will increase your token usage significantly"; one user "Spent around 50 USD on a failed project, context contaminated" (raminf, prash2488, [verified] https://news.ycombinator.com/item?id=45181577).
- Babysitting: it is "a pilot landing a plane all day long, and not what I signed up for" (medi8r, [verified] https://news.ycombinator.com/item?id=47218318). Subagents "are black boxes" (d4rkp4ttern, [verified] https://news.ycombinator.com/item?id=45181577). Hashimoto turns notifications off: "it was my job as a human to be in control of when I interrupt the agent, not the other way around", and keeps a background agent busy for only "10 to 20% of a normal working day" ([verified] https://mitchellh.com/writing/my-ai-adoption-journey).

**What makes a workflow portable.**
- Skills: "a skill is a Markdown file telling the model how to do something"; "Each skill only takes up a few dozen extra tokens"; "nothing at all preventing them from being used with other models"; and "almost everything I might achieve with an MCP can be handled by a CLI tool instead" (Simon Willison, [verified] https://simonwillison.net/2025/Oct/16/claude-skills/).
- Every calls its loop "tool-agnostic" (Claude Code, Droid, Codex CLI), with lessons stored as "prompts that live inside of your codebase or in plugins like ours" ([verified] https://every.to/chain-of-thought/compound-engineering-how-every-codes-with-agents).
- Users disagree about instruction files. One says "Putting hours into creating a good AGENTS file ... improved results a lot" (downsplat). Others report "claude regularly ignores explicit instructions in CLAUDE.md" (xenadu02), call skills "the junk drawer in the kitchen" (superfrank), and object to "potentially pointless constraints and instructions" (Izmaki) ([verified] https://news.ycombinator.com/item?id=48289950).

**What makes a good home for agents.**
- Fast, quiet, self-explaining tools: "The quicker they respond (and the less useless output they produce) the better"; "Tools must clearly inform agents of misuse or errors"; log to files so "the agent can read the log file"; "Simple code significantly outperforms complex code in agentic contexts"; MCP only "if the alternative is too unreliable" (Armin Ronacher, [verified] https://lucumr.pocoo.org/2025/6/12/agentic-coding/).
- Harness engineering: "anytime you find an agent makes a mistake, you take the time to engineer a solution", and "Each line in that file [AGENTS.md] is based on a bad agent behavior" (Mitchell Hashimoto, [verified] https://mitchellh.com/writing/my-ai-adoption-journey). Huntley's version is tuning Ralph "like a guitar" with signs in the prompt ([verified] https://ghuntley.com/ralph/).
- One build/run file in context every loop: "The @AGENT.md is the heart of the loop. It instructs how Ralph should compile and run the project" (Huntley, [verified] https://ghuntley.com/ralph/).
- Isolation and trust: Willison runs YOLO mode only "for tasks where I'm confident malicious instructions can't sneak into the context" ([verified] https://simonwillison.net/2025/Oct/5/parallel-coding-agents/).

Net: practitioners agree on one implementer (or 2-3 on disjoint work), many reviewers, strong back pressure from tests and builds, a lean instruction file grown from observed mistakes, and specs written before the run. None of the sources opened supports a standing role hierarchy for implementation, and several call it overhead.

### More implications for the den

13. Keep implementation at one developer per ticket, and spend multi-agent budget on review lenses (code-reviewer, qa, security in parallel). This matches Every's 12-reviewer pattern and HN's "subagents for context, not roles" view. https://every.to/chain-of-thought/compound-engineering-how-every-codes-with-agents , https://news.ycombinator.com/item?id=45181577
14. Treat the user's review attention, not agent count, as the throughput limit. Have the den show one landing-ready change at a time, and put spec quality before parallelism. https://simonwillison.net/2025/Oct/5/parallel-coding-agents/ , https://news.ycombinator.com/item?id=47218318
15. Make the den pull-based: batch agent results for the user to collect, rather than having agents interrupt. Hashimoto's "control of when I interrupt" fits the "waiting on user" queue better than pings. https://mitchellh.com/writing/my-ai-adoption-journey
16. Grow CLAUDE.md and the role files only from logged mistakes (the friction log feeding `correct`), one line per behavior, and prune lines no mistake justifies. Users report bloated instruction files get ignored. https://mitchellh.com/writing/my-ai-adoption-journey , https://news.ycombinator.com/item?id=48289950
17. For portability, prefer skills and CLI scripts over new MCP servers: they are cheap in context and run across vendors (Claude, Codex). Use the plugin to bundle them, not to replace them. https://simonwillison.net/2025/Oct/16/claude-skills/ , https://lucumr.pocoo.org/2025/6/12/agentic-coding/
18. Audit the den's own tools against Ronacher's checklist: fast, little output, errors that say how they were misused, logs written to files. `npm test` noise and board CLI errors are the first candidates. https://lucumr.pocoo.org/2025/6/12/agentic-coding/
